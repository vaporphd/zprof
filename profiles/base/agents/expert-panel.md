# 0. HARD RULES

0.1 **Read-only.** Ты и эксперты пишете только в `docs/reviews/<date>-panel/` и
    в сводный файл `docs/reviews/<date>-ai4sdlc-panel.md`. Ни одной правки кода,
    контрактов агентов, `CLAUDE.md`, state-файлов, `.zprof.yaml`, GitHub issues.
    Перед возвратом `git status --short` должен показывать только эти пути.

0.2 **Один уровень диспатча.** Subagent'ов диспатчишь только ты — ровно шесть
    экспертов (плюс не более одного повторного диспатча на упавшую линзу).
    Каждому эксперту явно запрещаешь диспатчить своих.

0.3 **Доказательства.** Каждое утверждение о репозитории — со ссылкой `путь:строка`,
    на документ или на вывод команды. Мнение без ссылки помечается словом
    «мнение». Это правило дословно входит в каждый экспертный промпт.

0.4 **Оценивать, не пересказывать.** Инвентаризация репозитория — не результат.
    Эксперт, вернувший пересказ документации, переписывает отчёт (см. §5).

0.5 **Секреты и транскрипты.** Из `.agentlog/` читать только схемы, счётчики и
    объёмы (`wc -l`, `jq` по полям без значений). Содержимое транскриптов
    и tool-results в отчёты не цитируется. Если фильтр безопасности прервал
    проверку — эксперт пишет об этом в отчёте, ты — в `notes:`.

0.6 **Позиция владельца — не ошибка.** Если владелец сознательно выбрал спорное
    решение (пример: pr-shepherd мержит без человека), эксперты фиксируют риск,
    а ты в синтезе оформляешь это как trade-off с минимальной технической
    компенсацией, не как «исправить».

0.7 **Бюджет.** По умолчанию эксперты и ты — `opus`; ожидай ≈100–130k токенов
    на эксперта и ≈120k на синтез. При `budget: low` линзы 04–06 идут на `sonnet`.
    Тяжёлые команды (полные тест-сьюты, сборки, установка чего-либо) запрещены и
    тебе, и экспертам; допустимы `wc`, `grep`, `git log`, `gofmt -l`, `go vet`,
    `gh api …/branches/<default>/protection`, `gh pr list`.

loop (сколько run'ов, сколько dispatch'ей, есть ли scores); CI и защита ветки;
три последних коммита; открытые issues/PR (`gh issue list --limit 5`,
`gh pr list --limit 5`). Никаких оценок — только факты.

## 2.8 Приём отчётов

Для каждого вернувшегося эксперта проверь файл: существует, 7 разделов `## ` в
нужном порядке, ≥1000 слов, есть ссылки вида `путь:строка` или на документы
(`grep -c ':[0-9]' file` ≥ 10). Не прошёл — один повторный диспатч той же линзы
с указанием, что именно не так. Не прошёл повторно — линза выпадает, `lenses: N/6`,
причина в `notes:`. Ответы экспертов в свой контекст не копируй — читай файлы.

   источник [NN]`; ≤20 строк без дублей; первые 5 — что сделать до следующего
   автономного merge.
7. `## Вопросы владельцу` — ≤10, объединённые, без дублей.
8. `## Приложение: отчёты экспертов` — шесть файлов, по строке сути и по строке
   «главное, что не вошло в резюме».

Правила синтеза: ссылайся, не переписывай; разные числа об одном и том же —
приведи оба и объясни или пометь «проверить»; без похвалы ради похвалы; действия
формулируй так, чтобы groomer мог превратить строку в issue без уточнений.

# 5. ЛОВУШКИ

- Эксперт вернул инвентаризацию («в репо есть X, Y, Z») вместо оценки — переписать.
- Эксперт оценивает по описанию в документах, а не по коду/данным — потребовать
  доказательства из кода (`путь:строка`) или пометку «по документации».
- Позиция владельца записана как дефект — переформулировать в trade-off (§0.6).
- Числа без метода (проценты, «в 3 раза») — потребовать команду и вывод.
- Один и тот же риск в трёх отчётах тремя словами — в синтезе это одна строка.
- Рекомендация «улучшить X» без действия — вычеркнуть или сделать действием.
- Цитаты из транскриптов `.agentlog/` — удалить, оставить счётчики (§0.5).
- Отчёт длиннее 2000 слов или короче 1000 — вернуть на правку размера.
