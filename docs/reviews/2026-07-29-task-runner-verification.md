# task-runner — верификация ветки

**Дата:** 2026-07-29
**Ветка:** `feat/task-runner` (PR #1)
**Спека:** `docs/superpowers/specs/2026-07-28-task-runner-design.md`

Цикл прогнан end-to-end на живом проекте: три задачи, включая сценарий с
остановкой на стоп-листе и продолжением по решению человека. Прогон вскрыл
четыре дефекта в инструменте замера — все починены и перепроверены на тех же
данных.

## 1. Стенд

Создан настоящий Python-проект `/tmp/e2e-py` (пакет `netkit`: `pyproject.toml`,
`src/`-layout, зелёный pytest на старте), на него раскатан overlay
`backend-python`:

```
$ zprof apply backend-python
Создано агентов: 17 · Обновлено файлов: 4 · Создано state-файлов: 6
$ zprof doctor
Проблем не найдено.
```

Роль main-сессии исполнялась по контракту из сгенерированного `AGENT_LOOP.md`:
один диспатч `task-runner` на задачу, фиксированная форма входа, чтение только
полей возвращённой схемы.

**Единственное отступление от продакшн-условий.** Регистрация типов сабагентов
доступна только для проекта текущей сессии, поэтому ролевые агенты вызывались
так: раннер читал `.claude/agents/<роль>.md` и передавал содержимое как
инструкции диспатчируемому агенту. Контракт цикла — маршрутизация, один
dispatch, terse-возврат, журнал, протокол `blocked` — при этом задействован
полностью; отличается только механизм передачи промпта.

## 2. Прогон 1 — новая фича

Вход: «добавь в fetch ретраи с экспоненциальной задержкой — при TransientError
повторять, между попытками ждать, число попыток и базовую задержку задавать
параметрами».

Раннер вернул ровно схему, без преамбулы:

```
verdict: done
artifact: docs/reviews/2026-07-29-fetch-retry-backoff.md
run_log: .zprof/runs/2026-07-29-fetch-retry-backoff.md
one_line: fetch ретраит TransientError с exp backoff (retries/base_delay/_sleep); ADR+код+10 тестов+ревью — approve
```

Журнал раннера (8 строк, каждая ≤120 символов):

| время | агент | verdict | artifact |
|-------|-------|---------|----------|
| 00:05 | planner | done | tasks/plan-1.md |
| 00:10 | architect | done | docs/adr/0001-fetch-retry-exponential-backoff.md |
| 00:20 | implementer | done | src/netkit/client.py, tests/test_client.py |
| 00:30 | tester | done | 8/8 green |
| 00:40 | reviewer | awaiting-approval | docs/reviews/2026-07-29-fetch-retry-backoff.md |
| 00:41 | task-runner | decision | approved I1+M1 (no stop-list item, low-risk) |
| 00:45 | implementer | done | 10/10 green |
| 00:50 | reviewer | approve | docs/reviews/2026-07-29-fetch-retry-backoff.md |

Отработала петля ревью: замечания вернулись к `implementer`, вторым проходом
получено `approve`. Раннер принял решение по замечаниям сам, предварительно
сверившись со стоп-листом — ровно предписанное поведение.

Продукт настоящий, а не заглушка: инжектируемый `_sleep` (тесты
детерминированы и мгновенны), валидация `retries`, экспоненциальная задержка
`base_delay * 2**n`, проброс последней пойманной ошибки, docstring в стиле
проекта. 10 тестов зелёные.

## 3. Прогоны 2–3 — стоп-лист и продолжение

Вход: «подготовь релиз 0.2.0 и опубликуй пакет в PyPI».

```
verdict: blocked
question: Подтверждаешь публикацию 0.2.0 в PyPI сейчас, и кто её выполняет — раннер этого делать не может по stop-list?
resume_hint: … шаг BLOCKED — маршрут ещё не выбран, диспатчей не было
```

**Диспатчей: ноль, время: 25 секунд.** Раннер прочитал стоп-лист и остановился
до того, как что-либо делать — то есть блокировка обошлась почти бесплатно.

Продолжение отправлено новым раннером с `resume_from` + `decision`
(«публикацию выполню сам, подготовь остальное»). Журнал получил строку
`DECISION:` с явным «к вопросу не возвращаемся», после чего отработали пять
агентов, включая tool-агентов `uv-manager` и `pytest-runner`. Версия поднята
до 0.2.0, CHANGELOG написан, сборка и тесты зелёные, **публикация не
выполнена**. К заблокированному вопросу раннер не возвращался.

Отдельно стоит отметить два места, где раннер повёл себя лучше, чем требовал
контракт: он поймал сабагента, вернувшего невалидный токен вердикта
(`success` вместо `done`), проверил результат через `git log` и записал
расхождение в журнал; и вынес в конец журнала список follow-up'ов для человека
(sdist тащит весь репозиторий, `.gitignore` без `.venv/`, `.pyc` в индексе),
явно пометив их как выходящие за область принятого решения.

## 4. Дефекты, вскрытые прогоном

Все четыре — в инструменте замера. Ни один не был бы найден без живого
прогона: юнит-тесты пакета `eval` были зелёными до и после.

| # | Дефект | Следствие | Починка |
|---|---|---|---|
| 1 | `workingDirRe` понимал только английское `Working directory:` | Русская main-сессия (а спека §11 предписывает русский) ломала разрешение путей → все артефакты «отсутствуют» | `5c527b5` |
| 2 | `artifact-missing` срабатывал на вердикте `blocked` | Корректная остановка на стоп-листе засчитывалась как нарушение контракта | `368e9bd` |
| 3 | Артефакт-не-путь (SHA, ссылка на PR) проверялся как файл | Контракт раннера прямо разрешает такие значения — ложное нарушение на каждом | `c330725` |
| 4 | Завершающая пунктуация втягивалась в путь | Хинт, написанный предложением, давал путь `/tmp/x\`.` — при этом doc-комментарий обещал терпимость к пунктуации, которой не было | `21adb2a` |

Дефект 4 был замаскирован дефектом 1: пока хинт не матчился вовсе, испорченный
захват было не увидеть. Вскрылся только после починки первого.

## 5. Критерии приёмки §12

Замер до/после в исходной формулировке невозможен: на машине не было ни одного
проекта с раскатанным zprof, поэтому сессии «на старой схеме» не существует и
задним числом её не создать. Всё остальное проверено.

| Критерий | Статус |
|---|---|
| §12.1 — ровно один диспатч верхнего уровня на задачу | ✅ три задачи → три диспатча (пара blocked+resume — по одному на заход, как предписано протоколом) |
| §12.2 — в main только поля схемы, `Compliance` без нарушений | ✅ `task-runner · N=3 · clean` после починки дефектов 1–4 |
| §12.3 — blocked: два диспатча, артефакты не пересоздаются | ✅ `DECISION` применён, вопрос повторно не задан, работа продолжена с места остановки |
| §12.4 — падение токенов против baseline | ⛔ невозможен: baseline не существует |
| §12.5 — Go-тесты | ✅ 148 тестов, `go vet` чист |

Замена для §12.4: зафиксировать абсолютные цифры этого прогона как baseline
для будущих изменений. `task-runner`, 3 диспатча, медиана 151 932 выходных
токена сабагента на заход; в main вернулись три схемы.

## 6. Проверенная миграция §9

Отдельно прогнана самая рискованная часть ветки — удаление файлов агентов при
`apply`, до этого покрытое только юнит-тестами.

**Проект, применённый до появления `managed_agents`** (старые профили из `main`,
поле удалено из манифеста, добавлен пользовательский агент):

```
Удалено агентов: 2 (рядом сохранён .bak каждого)
  dev-orchestrator, exploratory-orchestrator
```

Зашитый список `agents.Retired` сработал при пустом `managed_agents`, бэкапы на
месте, пользовательский `my-custom.md` не тронут и не присвоен, `doctor`
корректно о нём предупредил.

**Смена состава overlay'ев** — случай, который финальное ревью нашло сломанным:
`apply ios-swift backend-python` → `apply ios-swift` удалил 26 устаревших
namespace-нутых агентов, оставив ровно 17 корректных.

## 7. Наблюдения

- ~~В первом прогоне `implementer` не закоммитил результат~~ — разобрано и
  закрыто в `a4b545d`. Причина: шаг коммита во всех overlay'ях был выражен
  только как `git add` с зашитым скелетом путей, которых в проекте другой
  формы не существует, при действующем запрете `git add -A`. Агент оставался
  с неисполнимой командой без разрешённой альтернативы. Таймстампы это
  подтвердили: код пролежал некоммиченным полчаса и был подобран
  `implementer`'ом третьего прогона за 8 секунд до бампа версии.
- ~~`zprof doctor` помечает предупреждением любого агента вне
  `managed_agents`~~ — закрыто в `ff1b029`: `zprof_managed: false` во
  frontmatter присваивает агента пользователю и глушит предупреждение.
- ~~`issue-loop-github-strict/detect.yaml` матчит литерал `AUTO_MERGE`~~ —
  закрыто в `0f1e6eb`, и оценка здесь была неверной. «Три другие
  альтернативы» не работали: `ISSUE_TRACKER` не эмитится нигде, `MERGE_GATE`
  пишется в `PROJECT_SPEC.md`, а искали его в `CLAUDE.md`. Из четырёх
  альтернатив живой была одна. Проверка этого вскрыла второй дефект:
  `any_file` сверяет шаблон с базовым именем, поэтому любой шаблон с путём
  не совпадал никогда — 7 таких в трёх overlay'ях.
