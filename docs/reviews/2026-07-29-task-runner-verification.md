# task-runner — верификация ветки

**Дата:** 2026-07-29
**Ветка:** `feat/task-runner` (PR #1)
**Спека:** `docs/superpowers/specs/2026-07-28-task-runner-design.md`

## Что здесь и чего здесь нет

План предполагал задачи 0 (baseline) и 8 (шейкдаун) — прогнать одну и ту же
задачу на старой и новой схеме в живом проекте и сравнить токены, вернувшиеся
в main-контекст.

**Этот замер невозможен, и вот почему.** На машине нет ни одного проекта с
применённым zprof: поиск `.zprof.yaml` по `/Volumes/mydata/projects` не дал
ничего. zprof ещё ни разу не раскатывали на реальный проект. Сравнивать «до» и
«после» не с чем — обеих сессий не существует, и задним числом их не создать.

Вместо подгонки под несуществующий baseline здесь проверено то, что проверяемо
без живого проекта, и явно отмечено, что осталось непроверенным.

## 1. Миграция §9 — проверена end-to-end

Самая рискованная часть ветки: `apply` теперь удаляет файлы агентов. До сих пор
это покрывали только юнит-тесты на `PruneOrphanAgents`; целиком через CLI
сценарий не гонялся ни разу.

### Сценарий A — проект, применённый до появления `managed_agents`

Воспроизведён точно: старые профили взяты из `main` через `git archive`,
применены к чистому каталогу, затем ключ `managed_agents` удалён из
`.zprof.yaml` (валидным YAML-редактированием — так выглядит проект, который
раскатывал прежний бинарь). Добавлен пользовательский агент `my-custom.md`,
которого zprof никогда не писал.

```
$ zprof apply ios-swift          # новые профили = апгрейд
Создано агентов: 17
Обновлено файлов: 4
Создано state-файлов: 0
Удалено агентов: 2 (рядом сохранён .bak каждого)
  dev-orchestrator, exploratory-orchestrator
```

Результат:

| Проверка | Итог |
|---|---|
| Оркестраторы удалены (зашитый список `agents.Retired` сработал при пустом `managed_agents`) | ✅ |
| Бэкапы обоих на месте (`*.md.zprof.bak-<ns>`) | ✅ |
| `task-runner.md` записан | ✅ |
| Пользовательский `my-custom.md` не тронут | ✅ |
| `my-custom` не попал в `managed_agents` — zprof его не присваивает | ✅ |
| `zprof doctor` предупреждает про `my-custom` как про файл, который сам не удалит | ✅ |

Это ровно то поведение, ради которого §9 писался: без зашитого списка апгрейд
оставил бы рабочий `dev-orchestrator`, и main продолжила бы его диспатчить.

### Сценарий B — смена состава overlay'ев

Тот случай, который финальное ревью нашло сломанным (`cmd/apply.go` не переносил
`managed_agents`, и общее правило сирот никогда не срабатывало).

```
$ zprof apply ios-swift backend-python   # namespace: architect-ios, architect-py, ...
$ zprof apply ios-swift                  # откат до одного overlay
Создано агентов: 17
Удалено агентов: 26 (рядом сохранён .bak каждого)
  alembic-manager-py, architect-ios, architect-py, ... xcodegen-driver-ios
```

26 = 13 агентов `-py` (overlay убран) + 13 агентов `-ios` (при одном overlay
namespace не применяется, поэтому все имена сменились). После отката в
`.claude/agents/` остались ровно 17 корректных файлов без суффиксов, ни одного
`*-py.md` или `*-ios.md`.

Без исправления финального ревью все 26 остались бы в проекте валидными и
диспатчабельными навсегда.

## 2. Инструмент замера — работает

`zprof eval` прогнан на реальном логе сессии, в которой исполнялась эта ветка
(19 диспатчей сабагентов, 14ч45м):

```
Main-loop tokens: in 2,426 / out 534,625
Subagent tokens (output only): 2,222,056 across 19 dispatches
```

Инструмент корректно распарсил лог, посчитал токены по ролям, выдал
scorecard и список нарушений контракта. Добавленный в этой ветке токен
`task-runner` в `roleGuessRe` сработал — один диспатч классифицирован как
`task-runner`, остальные как `other`.

**Важная оговорка про 19 нарушений `return-preamble`.** Они ожидаемы и не
являются дефектом: диспатчились агенты типа `general-purpose` без контракта
`return_format`, а не zprof-роли. Инструмент честно отметил, что первая строка
ответа не `verdict:`. На проекте с раскатанным профилем эти же проверки будут
осмысленными.

Соотношение 2 222 056 против 534 625 — иллюстрация того же принципа, который
формализует ветка: около 80% работы прошло вне главного контекста. Но это
**не** измерение критерия §12.4: здесь нет ни старой схемы для сравнения, ни
раннера в роли контроллера.

## 3. Что осталось непроверенным

| Критерий §12 | Статус |
|---|---|
| §12.1 — ровно один диспатч верхнего уровня на задачу | не проверен: нужен живой прогон раннера |
| §12.2 — `Compliance` без нарушений | не проверен там же; предпосылки исправлены (`knownRoles` знает все 17 целей `next:`) |
| §12.3 — задача с `blocked`: два диспатча, `plan-N.md` не пересоздан | не проверен |
| §12.4 — падение токенов в main против baseline | **невозможен**: baseline не существует и не может быть снят задним числом |
| §12.5 — Go-тесты | ✅ 137 тестов, `go vet` чист |

### Как закрыть остаток

Нужен первый реальный проект с раскатанным zprof. Порядок:

1. `zprof init` в подходящем проекте, `zprof doctor` — чисто.
2. Прогнать типовую задачу, дав формулировку естественно, без подсказок про
   раннера: проверяется в том числе, распознает ли main границу «мутация —
   раннеру».
3. `zprof eval <sessionId>` — посмотреть число диспатчей верхнего уровня и
   `Compliance`.
4. Отдельно — задача, упирающаяся в стоп-лист, для проверки протокола `blocked`
   и `resume_from` + `decision`.

§12.4 в исходной формулировке закрыть уже нельзя. Разумная замена — снять
абсолютную цифру на первом же прогоне и зафиксировать её как baseline для
будущих изменений.

## 4. Наблюдения

- `zprof doctor` помечает предупреждением любого агента, которого нет ни в
  `managed_agents`, ни в источниках. Для легитимного пользовательского агента
  это шум: формулировка сообщения объясняет, что zprof его не удалит, но
  выглядит как замечание. Стоит подумать про способ пометить агента «мой,
  не трогать» — например отдельным ключом в `.zprof.yaml`.
- `issue-loop-github-strict/detect.yaml` матчит литерал `AUTO_MERGE` для
  распознавания секции спеки проекта. Ветка убрала флаг из поставляемых
  шаблонов, поэтому у новых проектов этот литерал не появится. Детект
  продолжит работать по трём другим альтернативам, но одна из четырёх со
  временем станет мёртвой.
