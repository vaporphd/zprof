# Панель AI4SDLC · 02 — инженерия оркестрации

**Линза:** топология dispatch, контракты, изоляция контекста, отказоустойчивость, бюджеты.
**Объект:** zprof main @ ed75196, прежде всего `profiles/base/agents/task-runner.md` (TR), `agent-loop-router.md`, `auditor*.md`, `telemetry.yaml`, дизайн-доки v2 и MEA.

## Вердикт

- **Топология разумна для одной задачи и оканчивается на ней.** Схема «main → один task-runner → плоские роли» с явным запретом рекурсии (TR:157-161) держит глубину 2. Длинный поток (бэклог, смены, стагнация) спроектирован только на бумаге (`docs/llm-team/2026-08-09-agent-hierarchy-v2.md` §3, §12), а depth 3 не проверен (там же, §14.7).
- **`return_format` — это соглашение, а не протокол.** Нет ни схемы, ни runtime-валидации. Парсер коллектора ищет строку `verdict:` уже после завершения dispatch (`profiles/base/zprof-collect.py:1388-1396`). Словарь вердиктов распался на ~30 токенов, а TR умеет обрабатывать только три.
- **Изоляция main работает как дисциплина промпта.** Инженерной гарантии нет. Вариант с hook отвергнут, потому что PreToolUse не отличает main от subagent (`docs/superpowers/specs/2026-07-28-task-runner-design.md:291-296`). Сам раннер собирает выводы детей в своём контексте без лимита.
- **Отказоустойчивость покрывает «громкие» отказы и пропускает тихие.** Круг tester↔implementer ограничен (TR:150-152), non-schema получает один повтор (TR:153-154). Глобальный бюджет dispatch существует только при `audit.enabled: true`, а он по умолчанию выключен (TR:195-197, 244-245). Таймаутов и лимитов токенов на dispatch нет. Неизвестные вердикты (`approve-with-fixes`, `awaiting-approval`, `merged-stamped`) никак не маршрутизируются.
- **Концептуально zprof близок к state of the art** (planner–executor–verifier + MEA claim≠fact + телеметрия уровня SRE). Главный долг — механизация контрактов: сегодня они держатся на промптах, а должна быть машинная проверка.

## Сильные стороны

1. **Явная граница мутации.** Одна точка входа для изменений и фиксированная форма dispatch с дословным `task` (`agent-loop-router.md:8-28`). Это чище, чем у большинства самодельных систем, где main делает «чуть-чуть сам».
2. **Протокол blocked→decision с анти-пинг-понгом.** Решение записывается как `DECISION`, повторно не спрашивается, частичный ответ — это вопрос только про остаток (TR:55-61). Протокол выстрадан (`tasks/lessons.md` L-001) и проверен вживую: 0 dispatch и 25 с до блокировки на стоп-листе (verification:83-91).
3. **MEA-петля claim→audit→state с integrity-снимками.** Аудитор не видит траекторию исполнителя (`auditor-deep.md`, раздел «Вход»). Git-снимки A/B с фильтром `.zprof/runs/*` (TR:212-218) дают runtime-проверку read-only, которой в MEA-paper нет в таком дешёвом виде.
4. **Счётчик считает и аудиторов** (TR:229), а после resume `claimed` деградирует в `pending` (TR:257). Подход консервативный и правильный: недоаудированное не считается доказанным.
5. **Телеметрия дерева dispatch** (`telemetry.yaml:17-21`: `parent_dispatch_id`, `spawn_depth`) и Class A-метрики контракта (`:43-47`). Отказы здесь наблюдаемы, а не только описаны.
6. **Запрет рекурсии раннера** сформулирован с обоснованием (TR:157-161), а не просто как запрет.

## Риски и слабости

1. **Фрагментированный словарь вердиктов.** Суть: у каждого overlay свой набор токенов (reviewer: `approve|changes-requested|blocked` в kotlin-jvm против `block|approve-with-fixes|approve|awaiting-approval` в пяти других; `fixed` у kotlin-jvm bug-hunter; `passed`, `clean`, `violations`, `partial`, `crashed`, `timeout`). Доказательство: frontmatter `profiles/overlays/*/agents/*.md`, а телеметрия вынуждена держать `review_block_verdicts` (`telemetry.yaml:103-106`) и `verdict_exempt_roles` для аудиторов с `completion:` (`:97-99`). Последствие: TR:143-154 определяет поведение только для `done/blocked/failed`, остальное интерпретирует LLM. Это главный источник недетерминизма маршрута.
2. **Контракты не валидируются в runtime.** Доказательство: `zprof-collect.py:1388-1403` вычисляет `return_parsed`/`has_preamble` post-hoc, а Python-hooks по конвенции всегда `exit(0)` (`CLAUDE.md`, Executing). Последствие: нарушение контракта видно в `zprof score`, но цепочку не останавливает. Роль retry-with-schema (TR:153) выполняет сам раннер-LLM, и это «проверка на честном слове».
3. **Нет глобального бюджета при audit off (режим по умолчанию).** Доказательство: бюджет живёт внутри секции «Аудит шагов» (TR:193-197, 242-251), лимит токенов и времени на dispatch отсутствует, сам long-horizon разбор признаёт «Нет формального лимита» (`2026-08-09-longhorizon-harness-comparison.md:71`). Последствие: цикл review↔implementer или blocked→сосед ограничен только переполнением контекста раннера, а это худший из возможных стоп-критериев.
4. **Контекст раннера растёт монотонно.** Доказательство: правило «читай только поля схемы» (TR:143) — пожелание, а текст ответа ребёнка целиком попадает в контекст раннера. Для feature-маршрута с аудитом это 7+ шагов × (исполнитель + аудитор). Последствие: на длинной задаче деградирует именно координатор. Смены PM в v2 (§3.2) решают ту же проблему на уровень выше, но не внутри задачи.
5. **Противоречия внутри доктрины.** Доказательство: Bash-allowlist TR:29-30 против `gh issue create`/PR TR:66-84; «один агент за раз» TR:142 против параллельных implementer в worktree `workflows/dev-pipeline.md:29-30`; маршруты TR:100-102 (с wiki-keeper и pr-shepherd) расходятся с `dev-pipeline.md:12-14`; `--delete-branch` против стоп-листа. Последствие: LLM разрешает противоречия по-разному от прогона к прогону. Именно так возникают лишние эскалации: lessons 2026-09-27 (2) описывает ровно такой случай с pr-shepherd.
6. **Resume покрывает только `blocked`.** Доказательство: вход `resume_from` описан в терминах `resume_hint` (TR:41, 52-54), а run log не пишет контрольных точек «шаг N начат». Последствие: после обрыва сессии или context exhaustion раннер не знает, закоммитил ли implementer. Верификация 07-29 уже зафиксировала некоммиченный код, подобранный чужим прогоном (verification:156-162).
7. **Изоляция main не механизирована.** Доказательство: отвергнутый PreToolUse-hook (design:291-296), в v2 он остаётся spike (§14.10). Последствие: любое внешнее skill-меню перебивает доктрину (lessons 2026-09-27 «Интеграция ветки»).
8. **Эмпирическая база тонкая.** Е2Е прогонялся с эмуляцией dispatch: роль-промпт передавался текстом (verification:29-34). MEA Stage 4 shakedown не выполнен (`mea-auditor/PLAN.md:39-45`), `.zprof/runs/` в самом репозитории пуст. Это мнение, но обоснованное: частоты отказов из карты выше неизвестны.

## Сравнение с практикой

1. **Planner–Executor–Verifier (Plan-and-Solve, LLM-Modulo).** zprof реализует его буквально, а verifier смотрит на среду, не на текст. Здесь zprof сильнее типичных реализаций, где verifier — это LLM-критик по диффу.
2. **MEA / LongHorizon-Harness (arXiv 2608.01964).** Взяты claim≠fact, requirements-state и integrity. Не взяты обязательность аудита (у zprof он opt-in, дефолт off) и потолок раундов N_max=25: у zprof потолок `max_dispatches`, и он тоже только при audit.
3. **Anthropic «Building effective agents».** Цепочка TR — это prompt chaining + orchestrator-workers с gates, в духе рекомендации «начинай с workflow, а не с автономного агента». Но рекомендация держать контракты инструментов строгими (ACI) не выполнена: вердикт — свободный токен, а не enum.
4. **OpenHands controller / SWE-agent.** У них есть `max_iterations`, budget в $ и stuck-detector (повтор одинаковых action/observation). У zprof аналог stuck-detector есть только post-hoc (P2 «blind retry» в `zprof score`, `telemetry.yaml:82-84`), в runtime его нет. Здесь zprof изобретает велосипед хуже оригинала.
5. **ReAct-петли.** Раннер фактически и есть ReAct над dispatch-действиями, но без структурированного observation: вывод ребёнка — это свободный текст. Структурированный observation (JSON) снял бы риски 1–2.
6. **Devin-подобные системы (долгоживущий planner + checkpointed state + human-in-the-loop).** zprof сильнее в явном протоколе эскалации и стоп-листе, но слабее в checkpoint/resume после обрыва: у Devin-класса систем состояние сессии восстанавливаемо.
7. **Temporal/durable workflows (SRE-практика).** Идемпотентные шаги, timeouts, retry policy с backoff и heartbeat. У zprof есть retry-count, остального нет. Это самый дешёвый источник заимствований.

## Рекомендации

- **Сейчас:** нормализовать вердикты в base-enum (`done|blocked|failed` + поле `detail:`) и добавить в TR таблицу маппинга overlay-токенов. Эффект: детерминированный роутинг и отсутствие неопределённых ветвей.
- **Сейчас:** вынести `max_dispatches` из секции аудита в глобальный бюджет раннера, действующий всегда. Эффект: закрывает бесконечные review↔implementer и blocked→сосед.
- **Сейчас:** устранить четыре противоречия доктрины (allowlist vs `gh`, parallel vs serial, маршруты TR vs dev-pipeline, `--delete-branch` vs стоп-лист) и вставить implementer в багфикс-маршрут. Эффект: меньше импровизации и лишних эскалаций.
- **Квартал:** SubagentStop-hook, который валидирует return против схемы из frontmatter и пишет `contract_violation` в run log так, чтобы раннер обязан был его прочитать. Эффект: контракт становится протоколом, а не просьбой.
- **Квартал:** checkpoint-строки `STEP-START/STEP-END` с SHA в run log и crash-resume по ним. Эффект: идемпотентное восстановление после обрыва.
- **Квартал:** Stage 4 shakedown MEA с включённым аудитом и измерением false-done/false-positive аудитора. Эффект: даёт числа для решения «audit on по умолчанию».
- **Позже:** runtime stuck-detector (повтор одинаковой пары агент+вердикт ≥2 → blocked) и per-dispatch timeouts через Workflow tool. Эффект: паритет с OpenHands-контроллером.
- **Позже:** перед миграцией на PM/TL сначала провести smoke-test depth 3 (v2 §14.7). Эффект: не строить иерархию на непроверенной платформе.
