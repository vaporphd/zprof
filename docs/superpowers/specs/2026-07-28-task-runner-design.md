# task-runner — вынос agent-loop из main-сессии

**Статус:** draft v1
**Дата:** 2026-07-28
**Автор:** Alex + brainstorming session
**Предшественник:** `2026-07-16-zprof-design.md` (§6 «Изоляция», T1–T4)

## 1. Проблема

Четыре уровня изоляции из v1 прячут *вывод* сабагентов, но не трогают
*контроллер цикла*. Сегодня петлю крутит main:

1. читает `AGENT_LOOP.md` (роутер) — что за задача, какой workflow;
2. читает `workflows/dev-pipeline.md` — какая цепочка агентов;
3. решает, кого диспатчить, и диспатчит;
4. пишет `followup.md`;
5. повторяет с шага 1.

Плюс `workflows/dev-pipeline.md` явно разрешает main'у ходить **мимо**
оркестратора: «Багфикс → `bug-hunter`», «Только тесты → `tester`»,
«Рефакторинг → `refactor-agent`». Каждый такой обход — прямой диспатч из
main со всеми последствиями.

Итог: `dev-orchestrator` спасает main только когда задача проходит полный
пайплайн. Во всех остальных случаях main остаётся диспетчером, накапливает
маршрутные решения, промежуточные вердикты и осколки контекста задачи.

## 2. Решение

Контроллер цикла переезжает в отдельного агента `task-runner`. Main
спавнит его на **одну задачу** и получает **одну схему**. Роутинг, выбор
маршрута, петля «тесты красные → назад к implementer», ведение журнала —
внутри раннера.

Граница ответственности:

| Запрос | Кто исполняет |
|---|---|
| Меняет репозиторий (фича, багфикс, рефактор, миграция) | `task-runner` |
| Не меняет (объяснить, показать дифф, обсудить, закоммитить, «как там раннер?») | main сам, обычными инструментами |

Правило одно и проверяется без толкований: **мутация → раннер, чтение → main**.

## 3. Не-цели

- Дрейн всей очереди одним раннером (`«выгреби todo.md»`) — контекст раннера
  растёт линейно, а компакцией внутри сабагента мы не управляем. v2.
- Механическое принуждение через `PreToolUse` hook — см. §11.
- `zprof run <task>` как отдельный headless-процесс — v2, см. §11.
- Пуш-уведомления на ключевых точках — v2.

## 5. Контракт `task-runner`

### 5.1 Frontmatter

```yaml
name: task-runner
description: >
  Владеет agent-loop целиком: принимает одну задачу, сам роутит,
  сам гоняет цепочку агентов, сам ведёт журнал. Диспатч на любой
  запрос, меняющий репозиторий. Trigger — EN: "implement", "fix",
  "refactor", "take next task". RU: «сделай», «почини», «отрефактори»,
  «следующая задача».
tools: Task, Read, Write, Glob, Grep, Bash
model: sonnet
return_format: |
  # CRITICAL: ответ начинается с `verdict:` — без преамбулы и код-фенса.
  verdict: done|blocked|failed
  artifact: <PR link | commit SHA | reports/*.md>
  run_log: .zprof/runs/<id>.md
  one_line: <≤120 символов>
  question: <только при blocked — что решить>
  resume_hint: <только при blocked — где остановились>
```

`Write` — только для журнала. `Bash` — только `date` и `git log -1`.
Раннер не пишет код, не запускает билды и тесты: это делают сабагенты.
Правило зафиксировано в теле промпта и наблюдаемо в трейсе `zprof eval`.

### 5.2 Вход

Main формирует фиксированную форму, не свободный текст:

```
task: <формулировка пользователя verbatim>
context_hint: <файл/модуль, если пользователь указал; иначе пусто>
resume_from: <путь к run-логу, если продолжение после blocked>
decision: <ответ пользователя на question, если resume_from задан>
```

`verbatim` принципиально: пересказ вносит интерпретацию main'а, и раннер
решает уже искажённую задачу.

### 5.3 Один спавн = одна задача

Раннер не берёт следующую задачу из `todo.md` по своей инициативе.
Закончил — умер. Следующая задача — новый спавн, свежий контекст.
Дрейфа контекста между задачами нет по построению.

## 6. Стоп-лист

### 6.1 Формат

Простые строки, читаемые моделью, а не regex — принуждение семантическое.

```yaml
# overlays/ios-swift/manifest.yaml
stop_list:
  - "загрузка билда в TestFlight или App Store Connect"
  - "смена bundle identifier, entitlements, provisioning profile"
  - "правка .xcodeproj руками вместо project.yml"
```

### 6.2 Базовый список (в `base/manifest.yaml`)

- force-push, rebase или amend опубликованной ветки;
- удаление веток и тегов;
- запись за пределы репозитория: БД, продовые конфиги, секреты;
- релиз, деплой, публикация пакета;
- слом публичного API, у которого есть внешние потребители;
- новая платная зависимость или новый внешний сервис;
- любая отправка содержимого репозитория наружу.

### 6.3 Видимость

Объединённый список (base + активные overlay'и) рендерится в `CLAUDE.md`
managed-блоком `stop-list`. Скрытой политики быть не должно: ты читаешь
её там же, где остальные правила проекта.

### 6.4 Поведение

Развилки **вне** стоп-листа раннер решает сам, опираясь на
`docs/PROJECT_SPEC.md`, существующие ADR и `lessons.md`, и фиксирует выбор
новым ADR. Развилка **на** стоп-листе — `blocked`.

## 7. Протокол `blocked` и resume

1. Раннер пишет в журнал строку `BLOCKED` с вопросом.
2. Возвращает `verdict: blocked` + `question` + `resume_hint` + `run_log`.
3. Main задаёт вопрос пользователю **дословно**, через `AskUserQuestion`.
   Пересказ запрещён: это уже интерпретация решения, которое принимает
   пользователь.
4. Ответ уходит **новому** раннеру: `resume_from: <run_log>` +
   `decision: <ответ>`.
5. Новый раннер восстанавливает состояние **из артефактов** — `plan-N.md`,
   ADR, коммиты уже на диске. Журнал служит только индексом, где
   остановились.

Пункт 5 — причина, по которой «свежий контекст каждый раз» (§5.3) не
стоит потерянной работы: состояние живёт в файлах, а не в контексте
раннера. Это T2 из v1-спеки, применённый к самому раннеру.

## 8. Журнал прогресса

### 8.1 Путь и формат

`.zprof/runs/<YYYY-MM-DD>-<slug>.md`, где `slug` — из формулировки задачи.

```markdown
# почини краш при старте на iOS 17
started: 2026-07-28T10:02 · overlays: ios-swift · route: dev-pipeline/bugfix

| время | агент | verdict | artifact |
|-------|-------|---------|----------|
| 10:02 | bug-hunter-ios | done | reports/crash-repro.md, failing test |
| 10:19 | implementer-ios | done | a3f91c2 |
| 10:24 | tester-ios | failed | 2 теста красные |
| 10:31 | implementer-ios | done | 91ba0e5 |
| 10:33 | tester-ios | done | 14 passed |

## Итог
verdict: done · artifact: PR #128
```

### 8.2 Правила

- Строка ≤120 символов, одна на шаг.
- Вывод сабагентов не вставляется. Иначе журнал станет тем же мусором,
  просто отложенным: на вопрос «как там» main втянет файл и утечка
  вернётся через заднюю дверь.
- Main читает **хвост** (последние ~10 строк), не весь файл, и только
  когда пользователь спросил.
- Отсутствие секции `## Итог` означает, что раннер не дошёл до конца.

### 8.3 Хранение

`.zprof/runs/` попадает в `.gitignore`. Автоочистки в v1 нет;
`zprof doctor` предупреждает при >50 файлов.

## 9. Миграция существующих проектов

Изменение ломающее. Ключевая проблема: `apply` только **пишет** агентов и
никогда не удаляет. После апгрейда `.claude/agents/dev-orchestrator.md`
останется сиротой — и main его дёрнет, потому что он валиден и описан.
Утечка сохранится ровно там, где мы её чиним.

**Решение.** `.zprof.yaml` += `managed_agents: [...]` — список имён,
записанных при последнем `apply`. На следующем `apply`:

- имя было в `managed_agents` и отсутствует в base+overlay источниках →
  файл удаляется, предварительно сохраняется `.bak`;
- имя отсутствует в `managed_agents` → это пользовательский агент,
  не трогается никогда;
- список перезаписывается актуальным составом.

Проекты, применённые до этого изменения, не имеют `managed_agents`.
Для них первый `apply` заполняет список и **ничего не удаляет по общему
правилу** — иначе рискуем снести пользовательских агентов, про которых не
знаем.

Исключение — **список известных упразднённых имён**, зашитый в CLI:
`dev-orchestrator`, `exploratory-orchestrator`. Эти файлы всегда
поставлялись zprof'ом и никогда не могли быть пользовательскими, поэтому
удаляются (с `.bak`) независимо от наличия `managed_agents`. Без этого
исключения апгрейд старого проекта оставлял бы сироту, которую §10
диагностирует как error, а `apply` не мог бы починить — тупик.

Остальных возможных сирот в старых проектах `zprof doctor` показывает
предупреждением, не удаляя.

## 10. Проверки `zprof doctor`

| Проверка | Уровень |
|---|---|
| `task-runner` присутствует в `.claude/agents/` | error |
| `dev-orchestrator` / `exploratory-orchestrator` отсутствуют | error |
| У каждого активного overlay непустой `stop_list` | error |
| У всех ролей есть `return_format` в frontmatter | error |
| `.zprof/runs/` присутствует в `.gitignore` | warn |
| Run-логов больше 50 | warn |
| Есть агенты не из `managed_agents` и не из источников (сироты) | warn |
| Агент помечен `zprof_managed: false`, но его даёт активный источник | warn |

Сироту можно присвоить: `zprof_managed: false` во frontmatter агента
глушит предупреждение для этого файла. Маркер живёт в самом файле, а не в
`.zprof.yaml`, чтобы удаление агента уносило и заявку на него — список в
манифесте пережил бы файл, который описывает. Присвоение агента, который
даёт активный overlay, вместо тишины даёт отдельное предупреждение:
следующий `apply` перезапишет файл, и молчание читалось бы как защита,
которой у пользователя нет.

## 11. Отвергнутые варианты

**Хук-предохранитель (`PreToolUse`).** Резать `Edit`/`Write`/мутирующий
`Bash` в main-сессии — единственный способ получить гарантию вместо
просьбы. Заблокировано фактом: документированная схема `PreToolUse` несёт
`session_id`, `transcript_path`, `cwd`, `tool_name`, `tool_input` — **поля,
отличающего main от сабагента, нет**. Событие `SubagentStop` существует
отдельно, то есть система про сабагентов знает, но в `PreToolUse` этого не
отдаёт.

Открытый эксперимент для v2: отличается ли `session_id` у сабагента от
main'а. Если да — вариант оживает. Парсинг `transcript_path` как
альтернатива отвергнут: хрупко.

**`zprof run <task>` — раннер отдельным процессом.** CLI спавнит headless
Claude Code с промптом раннера. Изоляция не по договорённости, а по
построению. Отложено: ломает «поговорить по ходу», требует headless-режима
и авторизации, и превращает zprof из генератора конфигов в ранер — это
отдельная подсистема, не правка профилей.

**Дрейн очереди одним раннером.** См. §3.

**Раннер на каждый overlay** (`task-runner-ios`, `task-runner-py`). Точнее
промпты, но девять копий логики цикла — гарантированный дрейф. Стек-специфика
и так приходит из `stop_list` и `workflows/*.md`, которые раннер читает в
рантайме.

## 12. Критерии приёмки

Измеряются через `zprof eval` — пакет уже парсит JSONL сессии в записи по
диспатчам с `SubagentTokens`, `ToolUses`, распарсенным `return_format` и
`Compliance`.

1. На одну задачу пользователя — **ровно один** диспатч верхнего уровня.
2. В main вернулись только поля схемы; `Compliance` без нарушений.
3. Задача, упёршаяся в стоп-лист: ровно два диспатча (первый + resume),
   при этом `plan-N.md` **не пересоздан** — resume продолжает, а не
   начинает заново.
4. Суммарные токены, вернувшиеся в main на одну задачу, ниже замера,
   снятого до изменения на той же задаче.
5. Go-тесты зелёные: парсинг `stop_list`, рендер managed-блока `stop-list`,
   проверки doctor, удаление осиротевших агентов, заполнение
   `managed_agents`.

Промпты юнит-тестами не покрываются. Для них — шейкдаун на живом проекте
плюс `zprof eval`, по образцу отчётов в `docs/reviews/` для pyweb и
kotlin-jvm.
