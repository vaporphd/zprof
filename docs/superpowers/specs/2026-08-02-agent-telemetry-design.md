# Телеметрия agent-loop и регулярный цикл улучшения

**Статус:** draft v1
**Дата:** 2026-08-02
**Автор:** Alex + brainstorming session
**Предшественники:** `docs/specs/2026-07-17-agent-eval-proposal.md` (Tier 1/2, панель судей), `docs/reviews/ios-model-eval/METHODOLOGY.md` (shakedown, асимметричная приёмка), `2026-07-28-task-runner-design.md` (журнал прогона)

## 1. Проблема

Сбор данных об agent-loop уже существует в трёх местах, но петля не замкнута — ничто не читает эти данные второй раз.

- `zprof eval` пишет `.zprof/eval/<sessionId>/summary.md` по ручной команде. Файл привязан к одной сессии, сравнить две сессии нечем.
- Журналы прогонов копятся в `.zprof/runs/` и не агрегируются.
- Матрицы model-routing прогнали один раз в июле, вывод записали в overlay'и, дальше он не перепроверяется.

Решение от 2026-07-17 прямо запрещало автоматизацию («manual only. No auto-run. No hooks»). Оно было верным для advisory-режима и здесь пересматривается.

Цель: **регулярный цикл eval → самоанализ → улучшение**, работающий в каждом проекте, для которого сгенерирован профиль.

## 2. Замеры, на которых стоит дизайн

Сняты 2026-08-02 на рабочей машине.

| Что | Значение |
|---|---|
| Проектов в `~/.claude/projects` | 19 |
| Файлов сессий (верхний уровень / со вложенными) | 343 / 1880, 1,3 ГБ |
| Окно ретенции JSONL | 2026-07-05 → 2026-08-02 = **28 суток**, ничего старше |
| `cleanupPeriodDays` | явно не задан, работает дефолт |
| Файлов `.output` в `/private/tmp/claude-501` | 155, до 120 КБ, старший — 29 июля |
| Окно жизни `.output` | **~3 суток** (чистка `/private/tmp`) |
| `task-notification` в 60 крупнейших файлах | 3425 |
| Из них с `subagent_tokens` / `tool_uses` / `duration_ms` | 2675 / 2674 / 2674 |
| Из них с `<usage>` | 2670 — парсер сейчас **не читает** |
| Записей с `isSidechain: true` в 120 крупнейших файлах | **0** |
| Оценка объёма | ~10⁴ диспатчей в месяц, ~10⁵ в год |
| Сборка | `CGO_ENABLED=0`, darwin+linux × amd64+arm64, бинарь 30,6 МБ |

Три следствия, определяющие дизайн:

1. **`isSidechain` не встречается ни разу.** Внутренностей субагента в JSONL нет. Раз `task-runner` разворачивает цепочку внутри себя, главный лог видит один диспатч раннера и ничего о маршруте. Маршрут добывается только из `.zprof/runs/*.md`.
2. **Три горизонта хранения:** `.output` ~3 суток, JSONL ~28 суток, наш стор — бессрочно. Самый богатый слой самый недолговечный.
3. **Объём мал.** 10⁵ записей в год — полный проход по JSONL в Go занимает доли секунды. SQLite окупается на 10⁶+, то есть не в этом десятилетии.

## 3. Принципы

**П1. Чужое хранилище с чужой политикой ротации — это уже потерянные данные.** `/private/tmp` чистит система, `~/.claude` чистит Claude Code. Любой дизайн, который приходит туда «потом», проектирует потерю. Захват — в момент, когда объект существует, в хранилище, которым владеем.

**П2. Никакой связности сверх формата файлов.** Проекты могут стоять на другой машине, где zprof не установлен. Сбор не должен зависеть от работы zprof.

**П3. Телеметрия каждого проекта живёт в этом проекте.** Общего места нет.

**П4. Данные готовы к слиянию с первого дня.** Возможен будущий слив с нескольких машин на один сервер. Закладывается сразу, потому что переделывать дорого.

**П5. Потери считаются и показываются.** Отчёт, не печатающий объём несобранного, врёт о том, на чём построен.

## 4. Архитектура

Три части, связанные **только форматом файлов**.

```
zprof apply (один раз)
      └──> кладёт сборщик в проект
                │
                ▼
проект работает сам ──> <project>/.agentlog/ ──> zprof stats <путь>
   (zprof не нужен)         (просто файлы)        (on demand, любая машина)
```

**Сборщик** — самодостаточный скрипт на python3 (есть на macOS и Linux из коробки). Устанавливается один раз при `zprof apply`. Дальше zprof ему не нужен.

**Данные** — `<project>/.agentlog/`. Копируются, переносятся, забираются с чужой машины.

**Анализ** — `zprof stats <путь> [<путь>…]`. Пути передаются явно; реестра и обхода корня нет.

Свойства: сломался zprof — сбор идёт; сломался сборщик — старые данные читаются; проект уехал на другой мак — пишет телеметрию сам.

### 4.1 Раскладка `.agentlog/`

```
<project>/.agentlog/
  dispatches.jsonl          строка на диспатч агента
  runs.jsonl                строка на задачу
  outcomes.jsonl            git-исход: SHA, дифф, переживаемость строк
  outputs/<dispatch_id>.gz  копии выводов субагентов
  configs/<sha>.json        снимки конфигурации, дедуп по хешу
  state.json                водяные знаки
  collect.log               ошибки и счётчик потерь
  schema.json               что именно пишет этот проект
  archive/                  dispatches-YYYY-MM.jsonl.gz
```

`.agentlog/` целиком добавляется в `.gitignore` — тем же механизмом, что уже добавляет `.zprof/runs/` (`apply/engine.go:147`, поле `gitignore:` в манифесте overlay'я).

### 4.2 Источники (только чтение)

| Источник | Что берём |
|---|---|
| `~/.claude/projects/<slug>/*.jsonl` | диспатчи, usage, verdict, `gitBranch`, `version`, `effort` |
| `/private/tmp/claude-501/<slug>/<sessionId>/tasks/*.output` | полный вывод субагента |
| `<project>/.zprof/runs/*.md` | маршрут цепочки — больше нигде не записан |
| `<project>/.claude/agents/*.md`, `.zprof.yaml` | `config_hash` |
| git | SHA, дифф, переживаемость строк |

Никаких записей за пределы `<project>/.agentlog/`. Это проверяется тестом: прогон сборщика на временной копии не должен создать ни одного файла вне проекта.

## 5. Схема записи

Две части.

**Ядро** — одинаково во всех проектах, только по нему возможно сравнение:

```
schema_version, machine_id, project_id, ts_utc,
session_id, dispatch_id, role, overlay, config_hash,
model, verdict, tokens_out, tool_uses, duration_ms,
artifact_exists, has_preamble, next_is_reachable,
output_ref, output_captured
```

**`ext`** — свободный JSON-объект. Стек или конкретный проект кладёт своё: iOS — время сборки и предупреждения `xcodebuild`, Python — дельту покрытия. Межпроектное сравнение `ext` не трогает.

Ядро плоское и типизированное, `ext` — одно поле. Переезд в SQLite при росте объёма остаётся механическим: `CREATE TABLE` плюс цикл вставки, `ext` — одна TEXT-колонка.

### 5.1 Готовность к слиянию

- `machine_id` — стабильный идентификатор машины, не имя хоста.
- `project_id` — стабилен при переименовании каталога; хеш первого коммита репозитория.
- `dispatch_id` глобально уникален (`toolu_…` уже такой).
- Никаких автоинкрементов и порядковых номеров — столкнутся при слиянии.
- Время в UTC со смещением.

Слияние = конкатенация файлов + дедупликация по `dispatch_id`.

### 5.2 Хранение

Старое **не удаляется**, только сжимается: `archive/dispatches-YYYY-MM.jsonl.gz`. При 10⁵ записей в год счёт идёт на десятки мегабайт.

Зачем нужны месяцы, при том что дашборд дрейфа неинтересен:

1. **Норма, от которой считается порог.** Уровень 1 (см. §7) срабатывает по выходу метрики за порог; порог берётся из накопленной нормы. Без неё — либо пороги из головы, либо ложные срабатывания.
2. **Редкие отказы.** Класс ошибки частотой раз на 200 диспатчей на окне в 50 невидим.
3. **Тихие изменения на стороне модели.** Модель за тем же именем меняется. Длинный ряд — единственный способ увидеть «ничего не трогали, а метрика поехала». Без него любое ухудшение спишется на последнюю правку контракта.

## 6. Сохранность

Пять правил, каждое закрывает конкретную дыру.

**С1. Копируем сразу, а не потом.** Вывод субагента живёт ~3 суток. Копируется **целиком** в момент, когда только что записан. 155 файлов × 120 КБ = 18 МБ сырья, в gzip около двух. Хранить хеш вместо файла — экономия на том, что стоит копейки, ценой невосстановимости.

**С2. Триггеров несколько, они перекрываются.** `SubagentStop` берёт вывод, `Stop` берёт срез лога, любой запуск сборщика догоняет пропущенное. Один не сработал — добирает следующий. Единственный триггер не сработает при краше, `kill` или засыпании машины.

**С3. Водяной знак двигается после записи, не до.** Сначала fsync, потом сдвиг. Иначе сбой записи означает вечный пропуск.

**С4. Потери считаются и печатаются.** Первая строка любого отчёта — сколько записей не собрано и почему.

**С5. Только дозапись.** Существующие строки не переписываются никогда.

### 6.1 Отказы

Сборщик вызывается из хука внутри петли агента, поэтому **никогда не роняет сессию**: любая ошибка — `exit 0`, запись в `collect.log`, инкремент счётчика потерь.

| Отказ | Поведение |
|---|---|
| `.output` уже стёрт | запись без него, `output_captured: false` — пропуск виден |
| JSONL ротировался | водяной знак указывает в никуда → пропуск помечается явно |
| Сессия активна, последняя строка обрезана | парсим до последней целой, знак не двигаем дальше |
| `.zprof.yaml` изменился посреди сессии | новый `config_hash` с этого диспатча |
| Диск полон / нет прав | `exit 0`, счётчик потерь, громко в отчёте |

## 7. Каденция: четыре уровня

Каждый уровень запускается **только по сигналу предыдущего**. Поэтому цикл может быть регулярным и не разорять.

| Уровень | Что | Цена | Триггер |
|---|---|---|---|
| **0. Запись** | сборщик пишет в `.agentlog/` | 0 токенов | каждая задача |
| **1. Арифметика** | детерминированные метрики, сравнение с предыдущим окном | 0 токенов | роль накопила N ≥ 5 новых диспатчей |
| **2. Самоанализ** | `evaluator` читает свод, контракт роли и сохранённые выводы | десятки тыс. токенов | сигнал уровня 1 |
| **3. Shakedown** | контролируемый эксперимент | десятки тыс. (общий) — миллионы (стековый) | предложена правка |

**Уровень 1 не требует доверия к модели.** Это счёт по фактам: соответствие контракту, доля возвратов не по схеме, ApT, число кругов `tester`. Он и есть фундамент; уровни 2–3 — суждение, и им нужна панель судей из спеки от 2026-07-17.

**Уровень 2 выдаёт не оценку, а диф к контракту роли.** Это главное отличие от июльской спеки: баллы никого не улучшают, улучшает предложенная правка текста.

Триггер — не календарь. Два условия: накопление (N ≥ 5) и выход метрики за порог относительно предыдущего окна.

## 8. Shakedown: зачем и какой

Телеметрия меряет **разные задачи разной сложности** — сказать по ней «роль стала хуже» нельзя, контроля нет. Shakedown даёт контроль: один вход, меняется ровно одна вещь.

- **Телеметрия отвечает «что-то изменилось»** — детект, дёшево, непрерывно.
- **Shakedown отвечает «изменилось из-за этого, стало лучше или хуже»** — атрибуция и приёмка, дорого, по требованию.

Без shakedown правка контракта — изменение без проверки.

### 8.1 Общий shakedown (новый)

Дешёвый smoke-тест контрактов. Большинство правок от стека не зависят: формулировка, схема возврата, границы полномочий, маршрутизация раннера, работа гейтов.

- крошечный фиксированный проект — fixture в репозитории zprof, **без внешнего тулчейна**;
- полный проход цепочки `task-runner → planner → architect → implementer → tester → reviewer`;
- проверяется **форма, а не содержание**: первая строка `verdict:` без преамбулы; обещанный `artifact:` существует на диске; `next:` ведёт в живую роль; гейты сработали в своих точках; раннер не спавнил раннера; журнал прогона заведён;
- гоняется на `haiku` — форму проверяет форма, не интеллект;
- цена — десятки тысяч токенов.

Смысл: ловит регрессию контракта **до раскатки на проекты**.

### 8.2 Стековый shakedown (существующий)

Как в `METHODOLOGY.md`: фиксированная фича MoodJournal, изолированные хосты, реальный тулчейн, дифференциальные прогоны через rsync замороженных фаз, асимметричное правило приёмки. 2,5–3 млн токенов на матрицу из семи прогонов.

### 8.3 Что когда гоняется

| Событие | Общий | Стековый |
|---|---|---|
| Правка контракта в `profiles/base/` | да | нет |
| Правка overlay-контракта | да | да |
| Смена тира модели | нет | да |
| Сигнал уровня 1 | да, первым делом | если общий чистый |

## 9. Права на правку

По масштабу последствий — тот же принцип, что в `agent-write-boundaries`.

| Объект правки | Кто применяет | Обоснование |
|---|---|---|

## 10. Две петли

| | Локальная | Глобальная |
|---|---|---|
| Кто читает | сам проект | zprof |
| Что читает | свою `.agentlog/` | телеметрию нескольких проектов |
| Что правит | свой `.zprof.yaml` | `profiles/base` и overlay'и |
| Пример | «в этом репо implementer тянет на sonnet, задачи мелкие» | «контракт reviewer после правки от 20.07 теряет артефакт» |

Ядро схемы существует ради глобальной петли: только по нему проекты сравнимы. `ext` — целиком для локальной.

## 11. Отчёты `zprof stats`

Первая строка каждого — счётчик потерь (С4).

1. **Здоровье роли** — pass@1, соответствие контракту, доля возвратов не по схеме, в разрезе роль × overlay × `config_hash`.
2. **Экономика и тиры** — ApT, стоимость задачи, где жгутся токены. Держит рекомендации по тирам живыми.
3. **Маршруты и застревания** — где цепочка уходит в `blocked`, как часто `tester` делает три круга, какие переходы мертвы. Источник — `runs.jsonl`.
4. **Дрейф профиля** — сравнение окон по `config_hash`. Низкий приоритет.

Рендер — существующий `render_html.go`.

## 12. Слой исхода

Локальный git, без внешних API.

- **Сразу:** SHA до и после задачи, статистика диффа.
- **Позже:** `--survival` — сколько строк агента дожило через N дней (`git log -S` по диапазону). Это настоящий acceptance-rate и заодно churn-сигнал.

Единственная часть системы, отвечающая на вопрос «стало ли лучше». Остальное меряет процесс.

## 13. Границы ответственности за разбор

Разбор логов Claude Code существует сегодня в Go (`cli/internal/eval/parser.go`). Новый сборщик — python3 в проекте. Две реализации одного разбора недопустимы, поэтому граница проводится явно:

| Кто | Что читает | Что пишет |
|---|---|---|
| **Сборщик (python3, в проекте)** | сырые логи Claude Code, `.output`, `runs/*.md`, git | `.agentlog/*.jsonl` |
| **zprof (Go)** | **только** `.agentlog/*.jsonl` | отчёты |

То есть Go-код перестаёт быть парсером сырых логов и становится читателем нормализованных записей. Извлечение целиком переезжает в сборщик — иначе zprof снова становится обязательным на каждой машине, а это нарушает П2.

Существующий `zprof eval` остаётся как есть, отдельным путём для разового разбора одной сессии. Его пересборка поверх `.agentlog/` — отдельная задача, в этот объём не входит.

Знание, которое переносится в сборщик из `parser.go`: сопоставление диспатчей с уведомлениями по `tool-use-id`, разбор `return_format`, проверки соответствия контракту, разрешение `Working directory:` для путей артефактов.

Плюс то, чего в Go-парсере нет и что сборщик должен уметь сразу: чтение `<usage>` (присутствует в 2670 уведомлениях из 3425, сейчас игнорируется) и инкрементальность через смещение.

## 14. Что добавляется

| Что | Почему |
|---|---|
| Сборщик `collector.py` в `profiles/base/` | извлечение из логов, П2 |
| `profiles/base/telemetry.yaml` + `profiles/overlays/*/telemetry.yaml` | ядро и расширения схемы |
| `apply` — раскатка сборщика, `schema.json`, хука в `<project>/.claude/settings.json`, записи в `.gitignore` | установка в проект |
| Команда `zprof stats <путь>` | чтение `.agentlog/` и отчёты |
| Команда `zprof shakedown --general` | общий smoke-тест контрактов |
| Fixture общего shakedown в репозитории | проект без внешнего тулчейна |
| `doctor` — проверка, что `.agentlog/` покрыт `.gitignore` | по образцу проверки №10 для `.zprof/runs/` |

`<project>/.claude/settings.json` — файл внутри проекта, не `~/.claude`. Домашний каталог остаётся источником чтения.

## 15. Декомпозиция

Объём больше одного плана реализации. Три этапа, каждый самостоятельно полезен:

**Этап 1 — сбор.** Сборщик, схема, раскатка через `apply`, хуки, `.gitignore`, проверка в `doctor`. Результат: данные копятся в каждом проекте, ничего не теряется. Ценность есть даже без единого отчёта, потому что без накопленных данных остальное невозможно.

**Этап 2 — чтение.** `zprof stats` и четыре отчёта, включая счётчик потерь. Результат: уровень 1 каденции работает.

**Этап 3 — цикл.** Общий shakedown с fixture, дифы к контрактам от `evaluator`, границы прав из §9. Результат: уровни 2–3 работают.

Пороги уровня 1 задаются между этапами 2 и 3, когда накопится первая норма.

## 16. Побочная выгода

`METHODOLOGY.md`, известное ограничение №2: поле `model:` в применённом overlay — **не то, что реально исполняется**, когда диспатч идёт из родительской сессии. Июльская матрица мерила не совсем прод.

Телеметрия меряет то, что реально исполнилось. Это чинит известную дыру протокола, а не просто добавляет цифры.

## 17. Открытые вопросы

- Срабатывает ли `SubagentStop` на диспатчи, порождённые `task-runner` внутри себя, или только на диспатчи из главной сессии. Проверяется замером, на дизайн не влияет: при отрицательном ответе маршрут всё равно берётся из `runs.jsonl`, а перекрывающиеся триггеры (С2) добирают вывод.
- Конкретные значения порогов уровня 1. Определяются после накопления первой нормы (§5.2), до этого уровень 1 только считает и печатает.
- Состав fixture общего shakedown: минимальный проект, который проходит всю цепочку без тулчейна.
