## 1. Проблема

Четыре решения, которые сегодня принять нечем.

1. **Стало ли лучше после правки контракта роли.** Правка в `profiles/` раскатывается на все проекты. Единственная проверка — стековый shakedown за 2,5–3 млн токенов, поэтому её не делают, поэтому регрессия контракта проходит незамеченной.
2. **Где цепочка застревает.** Куда уходит `blocked`, сколько кругов делает `tester`, какие переходы мертвы — известно по ощущениям, не по счёту.
3. **Сколько стоит задача и где жгутся токены.** Нет ни цифры стоимости задачи, ни разбивки по ролям.
4. **Какой тир модели ставить роли.** Матрицы model-routing прогнали один раз в июле, вывод записали в overlay'и, дальше он не перепроверяется — перепрогон стоит миллионы токенов.

Данные, из которых всё это выводится, уже порождаются — и стираются, потому что их никто не забирает.

Цель: **регулярный цикл сбор → арифметика → самоанализ → правка**, работающий в каждом проекте, для которого сгенерирован профиль.

Решение от 2026-07-17 прямо запрещало автоматизацию («manual only. No auto-run. No hooks»). Оно было верным для advisory-режима и здесь пересматривается.

## 2. Что порождает Claude Code

Замеры 2026-08-02 на рабочей машине. Числа приведены как порядки величин, а не как константы дизайна.

### 2.1 Раскладка на диске

```
~/.claude/projects/<slug>/
  <sessionId>.jsonl                        главный лог сессии
  <sessionId>/subagents/agent-<id>.jsonl   полный транскрипт сабагента
  <sessionId>/subagents/agent-<id>.meta.json
  <sessionId>/tool-results/<id>.txt        выгруженные крупные tool-выводы

/private/tmp/claude-501/<slug>/<sessionId>/tasks/*.output   ← зеркало, не оригинал
```

`meta.json` целиком:

```json
{"agentType":"nest-inner","description":"Dispatch nest-inner subagent",
 "toolUseId":"toolu_01DBgZdf2sEonXRmvUAcX13h",
 "parentAgentId":"a54a62add7dc3a394","spawnDepth":2}
```

### 2.2 Ключевые факты

| Что | Значение |
|---|---|
| Проектов в `~/.claude/projects` | 19, из них 14 имеют `subagents/` |
| Объём `subagents/` + `tool-results/` | 1123 МБ из 1,3 ГБ всего |
| gzip на не-base64 содержимом | 4,4–5,3× |
| `spawnDepth: 1` / `spawnDepth: 2` | 1463 / 73 — вложенные диспатчи пишутся |
| `/private/tmp/.../tasks/*.output` | побайтовое зеркало `subagents/` и `tool-results/` |

| Корневых коммитов в 25 реальных репозиториях | у всех ровно 1 |

### 2.3 Три следствия, определяющие дизайн

1. **Внутренности сабагента лежат на диске.** `isSidechain` в главном логе не встречается, но не потому, что данных нет: сабагенты вынесены в файлы-спутники, и `isSidechain: true` стоит в первой строке каждого такого файла. `meta.json` даёт `agentType`, `toolUseId`, `parentAgentId`, `spawnDepth` — всё дерево маршрута восстанавливается отсюда, машиночитаемо.

2. **Стоимость считается только из транскриптов.** Один диспатч: `input` 53 221, `cache_creation` 654 972, `cache_read` 18 651 281, `output` 58 761. В главном логе для диспатчей той же сессии `totalTokens` — 97 165, 97 254, 54 088. Разбивки по кешу в главном логе **нет вообще**, а кеш — 97% расхода и тарифицируется иначе. Без транскриптов проблема 3 из §1 не решается.

3. **Данные под чужим управлением надо копировать, а не читать по требованию.** `~/.claude` чистит Claude Code, `/private/tmp` чистит система. Числовые окна ротации к дизайну отношения не имеют: они определяют только, насколько плохо, если захват не сработал. Захват — в момент, когда объект существует.

## 3. Принципы

**П1. Данные копируются в наше хранилище сразу.** Не «читаются, когда понадобятся». Чужое хранилище с чужой политикой ротации — это спроектированная потеря.

**П2. Никакой связности сверх формата файлов.** Проекты стоят на разных машинах — на маке, на сервере, в облаке — и zprof там может быть не установлен. **Сбор не зависит от zprof ни в одной точке.**

**П3. Телеметрия каждого проекта живёт в этом проекте.** Общего места нет, реестра проектов нет, обхода корня нет.

**П4. Данные готовы к слиянию с первого дня.** Один проект может писать телеметрию с нескольких машин. Слияние закладывается сразу, потому что переделывать дорого.

**П5. Потери считаются и показываются.** Отчёт, не печатающий объём несобранного, врёт о том, на чём построен.

## 4. Архитектура

Три части, связанные **только форматом файлов**.

```
zprof apply (один раз)
      └──> кладёт сборщик в проект + прописывает хуки
                │
                ▼
Claude Code сам зовёт сборщик ──> <project>/.agentlog/ ──> zprof stats <путь>
   (zprof не нужен)                  (просто файлы)         (потом, с любой машины)
```

### 4.1 Сборщик

Один файл: `<project>/.claude/zprof-collect.py`. Скрипт на python3. Устанавливается один раз при `zprof apply`. Дальше zprof ему не нужен.

Запускает его **Claude Code**, через хуки в `<project>/.claude/settings.local.json`:

```json
{"hooks": {
  "SubagentStop":  [{"hooks": [{"type":"command","command":"test -x \"$CLAUDE_PROJECT_DIR/.claude/zprof-collect.py\" && \"$CLAUDE_PROJECT_DIR/.claude/zprof-collect.py\" subagent-stop || true"}]}],
  "Stop":          [{"hooks": [{"type":"command","command":"test -x \"$CLAUDE_PROJECT_DIR/.claude/zprof-collect.py\" && \"$CLAUDE_PROJECT_DIR/.claude/zprof-collect.py\" stop || true"}]}],
  "SessionStart":  [{"hooks": [{"type":"command","command":"test -x \"$CLAUDE_PROJECT_DIR/.claude/zprof-collect.py\" && \"$CLAUDE_PROJECT_DIR/.claude/zprof-collect.py\" session-start || true"}]}]
}}
```

**`settings.local.json`, не `settings.json`.** Второй обычно коммитится, и тогда хук выстрелит у коллеги, у которого скрипта нет. Цена решения: на машине, где `zprof apply` не делали, телеметрии не будет — но там и сборщика нет, так что выбор между «нет данных» и «нет данных плюс сломанный хук».

`test -x … || true` в самой команде — потому что «любая ошибка → `exit 0`» (§6.1) относится к скрипту, а отсутствующий файл падает в шелле **до** его запуска.

`<project>/.claude/settings.local.json` — файл внутри проекта, не `~/.claude`. Домашний каталог остаётся источником чтения и никогда не пишется.

**Раскладка хуков — отдельная работа, а не строка в таблице.** Сегодня `apply` умеет писать `.claude/agents/*` и managed-блоки в markdown через маркеры-комментарии (`managed.Merge`). JSON маркеров не держит, и ссылок на `settings*.json` в `cli/` нет ни одной. Нужен идемпотентный JSON-upsert: вставить три хука, не затерев чужие ключи, распознать ручную правку, уметь снять записи при откате, разрешить конфликт. По объёму сопоставимо со сборщиком.

Claude Code передаёт на stdin JSON. Реальный payload `SubagentStop` (проверено, см. §17):

```json
{"session_id":"…","cwd":"/path/to/project",
 "transcript_path":"/Users/…/.claude/projects/<slug>/<sess>.jsonl",
 "agent_id":"a54a62add7dc3a394","agent_type":"nest-outer",
 "agent_transcript_path":"/Users/…/<sess>/subagents/agent-a54a62add7dc3a394.jsonl",
 "last_assistant_message":"…",
 "background_tasks":[{"id":"a563…","agent_type":"nest-inner","status":"running"}]}
```

### 4.2 Что делает сборщик на каждом триггере

| Триггер | Действие |
|---|---|
| `SubagentStop` | записывает **указатель** в `state.json`: `agent_id`, `agent_transcript_path`, `toolUseId`, метка времени. Файл не копирует — он ещё дописывается (§6, С1) |
| `Stop` | копирует всё новое (алгоритм ниже), пропуская агентов, которые в `background_tasks` числятся `running` |
| `SessionStart` | то же для прошлых сессий, которые до `Stop` не дожили |

Алгоритм копирования:

0. Взять `flock` на `.agentlog/.lock` на весь проход (см. С6).
1. Прочитать `<project>/.agentlog/state.json` — до какого места дочитано:
   ```json
   {"sessions": {"1add3b3f-…": {"main_log_offset": 481234,
                                "main_log_size": 481234,
                                "main_log_head_sha": "…",
                                "agents_done": ["a54a62add7dc3a394"]}}}
   ```
2. Открыть главный лог **по `transcript_path` из payload хука**. Перед чтением сверить размер файла и хеш первых 4 КБ с сохранёнными: не совпало → перечитать с нуля (дедуп по `(dispatch_id, seq)` делает это безопасным). Совпало → перемотать на смещение и прочитать только новое.
3. Скопировать из `<sess>/subagents/` все `agent-<id>.jsonl` и `agent-<id>.meta.json`, чьих `<id>` нет в `agents_done` и которые не числятся `running`. Путь `<sess>/` выводится из `transcript_path` отбрасыванием `.jsonl`.
4. Скопировать новое из `<sess>/tool-results/`.
5. Разобрать скопированное в строки `.agentlog/*.jsonl`.
6. `fsync`, и **только потом** переписать `state.json` — через temp + `rename`.

Шаг 6 после шага 5 — это С3. Упало посередине — знак не сдвинулся, следующий запуск перечитает тот же кусок, дубли отсекутся по `(dispatch_id, seq)`.

### 4.2.1 Пути берутся из payload, а не восстанавливаются

**Правило: сборщик никогда не конструирует путь к логам Claude Code из `cwd`.**

Слаг каталога `~/.claude/projects/<slug>/` — не «абсолютный путь с заменой `/` на `-`». Заменяются и другие символы, и маппинг лоссовый:

```
/Volumes/mydata/projects/hft_moex      → -Volumes-mydata-projects-hft-moex     (_ → -)
/Volumes/mydata/projects/cmux_anywhere → -Volumes-mydata-projects-cmux-anywhere
/Users/alv/.hermes                     → -Users-alv--hermes                    (. → -)
```

Каталогов `hft-moex` и `cmux-anywhere` на диске нет — это перекодировка имени. Сборщик, идущий по правилу «заменить `/`», попадёт в несуществующий каталог и **молча вернёт ноль записей**.

Сверх того, слаг — функция корня проекта, а не `cwd`: сессии с `cwd = …/hft_moex/analysis/stale-entry` и `…/hft_moex/dashboard-web` лежат в слаге корня, отдельных каталогов под подкаталоги нет (20 слагов на всю машину). А в payload приходит фактический `cwd`, часто подкаталог.

Поэтому: **для текущей сессии — `transcript_path` из payload; для догона на `SessionStart` — соседние сессии того же проекта через `dirname(transcript_path)`.** `transcript_path` — контракт хука, перекодировка `cwd` — догадка о недокументированной функции на чужой стороне, которая разъедется молча.

### 4.2.2 Бюджет времени

Хук работает синхронно, пока пользователь ждёт. Порядок величин: один транскрипт — до 1,1 МБ, сессия на полсотни диспатчей — десятки мегабайт копирования и gzip. `SessionStart` с догоном мёртвых сессий хуже всего: он на старте.

Телеметрия, которую отключают из-за задержки, отменяет весь дизайн, а не ухудшает его. Поэтому:

- **бюджет 300 мс на синхронную часть.** В него укладываются: взятие лока, чтение `state.json`, дописывание указателей, копирование **сырых байт** без сжатия;
- **нормализация и gzip — в фоне.** Сборщик форкает отсоединённый процесс и сразу возвращает `exit 0`. Фоновый процесс держит тот же `flock`, поэтому следующий хук не наложится;
- бюджет исчерпан — недоделанное остаётся в `state.json` как незакрытое и доедается следующим проходом;
- `zprof stats` печатает, сколько проходов упёрлось в бюджет. Регулярное упирание — сигнал, а не норма.

Копирование байт дёшево, дорого сжатие и разбор — поэтому в синхронной части остаётся ровно то, что нельзя отложить: захват до того, как источник исчезнет.

### 4.3 Данные

`<project>/.agentlog/`. Обычный каталог, копируется, переносится, забирается с чужой машины по `scp`.

```
<project>/.agentlog/
  dispatches.jsonl          строка на диспатч
  runs.jsonl                строка на задачу
  outcomes.jsonl            git-исход: SHA, дифф, переживаемость строк
  transcripts/<agent_id>.jsonl.gz   копии транскриптов сабагентов
  tool-results/<id>.txt.gz  копии крупных tool-выводов
  raw/                      сырые срезы главного лога, до нормализации
  configs/<sha>.json        снимки конфигурации, дедуп по хешу
  state.json                водяные знаки и указатели
  collect.log               ошибки и счётчик потерь
  schema.json               что именно пишет этот проект
```

`.agentlog/` целиком добавляется в `.gitignore` функцией `ensureGitignore` (`cli/internal/apply/engine.go:281`). Список записей захардкожен там же, строка 288 — поля `gitignore:` в `profiles/base/manifest.yaml` нет, оно есть только у оверлеев. То есть добавление `.agentlog/` — правка Go-кода, а не данных профиля.

**Принятый риск: `git clean -xdf` сносит `.agentlog/` целиком**, потому что каталог гитигноренный и лежит в рабочем дереве. Свежий клон репозитория тоже даёт пустую историю телеметрии. Это осознанный размен: каталог внутри проекта переносится вместе с ним одним `cp -r`, что и есть свойство, ради которого выбрано это место (П3).

Смягчение, а не устранение:

- `doctor` предупреждает, что `.agentlog/` уязвим к `git clean -xdf`, и напоминает про бэкап при накопленном объёме выше порога;
- `doctor` проверяет **две разные вещи**: что `.agentlog/` присутствует в `.gitignore` и что он не попал в индекс git;
- рекомендация в документации: перед `git clean` в проекте с телеметрией сделать `cp -r .agentlog /somewhere`.

### 4.4 Анализ

`zprof stats <путь> [<путь>…]`. Пути передаются явно; реестра и обхода корня нет (П3). Читает **только** `.agentlog/`, никогда не читает `~/.claude`.

Свойства: сломался zprof — сбор идёт; сломался сборщик — старые данные читаются; проект уехал на сервер — пишет телеметрию там же, в свою `.agentlog/`.

## 5. Схема записи

Две части.

**Ядро** — одинаково во всех проектах, только по нему возможно сравнение:

```
schema_version, harness, harness_version, protocol_version,
machine_id, project_id, ts_utc,
session_id, dispatch_id, seq, parent_dispatch_id, spawn_depth,
role, overlay, config_hash,
model_requested, model_resolved,
verdict, status, dispatch_complete,
tokens_input, tokens_output, tokens_cache_read, tokens_cache_creation,
tool_uses, duration_ms,
artifact_exists, has_preamble, next_is_reachable,
transcript_ref, transcript_captured, transcript_truncated
```

**`ext`** — свободный JSON-объект. Стек или конкретный проект кладёт своё: iOS — время сборки и предупреждения `xcodebuild`, Python — дельту покрытия. Межпроектное сравнение `ext` не трогает.

Ядро плоское и типизированное, `ext` — одно поле. Переезд в SQLite при росте объёма остаётся механическим: `CREATE TABLE` плюс цикл вставки, `ext` — одна TEXT-колонка.

### 5.1 Поля, которых не было в v1, и зачем они

| Поле | Зачем |
|---|---|
| `harness`, `harness_version`, `protocol_version` | над проектами работает не только Claude Code (см. §16). Без этого поля записи двух систем неразличимы и слияние смешает их в одну норму |
| `seq` | один `task-id` уведомляет **несколько раз** — агента можно возобновить через `SendMessage`. Дедуп по `dispatch_id` съест продолжения |
| `parent_dispatch_id`, `spawn_depth` | дерево маршрута из `meta.json` |
| `model_requested` / `model_resolved` | A/B по тирам: запрошенный алиас и фактически исполнявшаяся модель — разные вещи |
| токены четырьмя полями | стоимость без разбивки по кешу не считается |
| `dispatch_complete` | для асинхронных диспатчей `tool_result` приходит **на запуск**. Наличие `tool_result` не означает завершения |
| `transcript_truncated` | сессию убили — транскрипт остался частичным. Молчащий недосчёт токенов запрещён (П5) |

### 5.2 Готовность к слиянию

- `machine_id` — стабильный идентификатор машины, не имя хоста.
- `project_id` — хеш корневого коммита репозитория. Проверено на 25 реальных репозиториях: у всех ровно один корень. При нескольких корнях (subtree-merge) выбор детерминированный — лексикографический минимум, не «первый попавшийся».
- **Фолбэк, когда корневого коммита нет.** Сборщик срабатывает по хуку в любом каталоге, включая не-git и репозиторий до первого коммита. Порядок разрешения: корневой коммит → если его нет, `machine_id` + абсолютный путь, с пометкой `project_id_provisional: true`. Как только первый коммит появился, сборщик записывает настоящий `project_id` и оставляет `project_id_previous` в той же строке — чтобы старые записи сшивались с новыми при слиянии, а не превращались в отдельный проект.
- `dispatch_id` — составной: `<harness>:<session_id>:<native_id>`. Нативный идентификатор глобально уникален только у Claude Code (`toolu_…`); у других систем это порядковый номер внутри сессии.
- Никаких автоинкрементов сверх `seq`, который всегда идёт в паре с `dispatch_id`.
- Время в UTC со смещением.

Слияние = конкатенация файлов + дедупликация по `(dispatch_id, seq)`.

### 5.3 Хранение

**Ничего не удаляется.** Транскрипты и сырьё жмутся gzip (4,4–5,3× на этих данных) и лежат бессрочно. Бюджет задаётся на проект в `.zprof.yaml`, по умолчанию — не ограничен. Чистка выполняется **только по явной команде** пользователя или команды, никогда автоматически.

Зачем нужны длинные ряды:

1. **Норма, от которой считается порог.** Метрики класса B (§7) сравниваются с накопленной нормой. Без неё — либо пороги из головы, либо ложные срабатывания.
2. **Редкие отказы.** Класс ошибки частотой раз на 200 диспатчей на окне в 50 невидим.
3. **Тихие изменения на стороне модели.** Модель за тем же именем меняется. Длинный ряд — единственный способ увидеть «ничего не трогали, а метрика поехала». Без него любое ухудшение спишется на последнюю правку контракта.
4. **Переразбор после смены формата.** Сохранённое сырьё позволяет перечитать историю новой версией парсера. Без сырья дыра навсегда.

## 6. Сохранность

**С1. Хук регистрирует, копирует проход.** Транскрипт сабагента **не дописан** в момент срабатывания `SubagentStop` — замерено: 3452 байта в момент хука против 5075 после, последний ход с `usage` пишется позже. Копирование в хуке даёт молча обрезанный файл и недосчитанные токены. Поэтому `SubagentStop` пишет указатель, а копирует `Stop`, пропуская агентов со `status: running` в `background_tasks`.

**С2. Триггеров три, они перекрываются.** `Stop` — основной путь. `SubagentStop` — гарантия, что указатель на диске раньше, чем сессия успеет упасть. `SessionStart` — подбирает сессии, убитые до `Stop`. Замерено: при `kill -9` в середине диспатча `SubagentStop` **не срабатывает**, но `meta.json` и частичный транскрипт остаются на диске и забираются следующим запуском.

**С3. Водяной знак двигается после записи, не до.** Сначала `fsync`, потом сдвиг. Иначе сбой записи означает вечный пропуск.

**С4. Потери считаются и печатаются.** Первая строка любого отчёта — сколько записей не собрано и почему. В этот же счётчик идёт нераспознанное (§13).

**С5. Только дозапись.** Существующие строки не переписываются никогда.

**С6. Взаимное исключение обязательно.** Два окна Claude Code в одном проекте — рядовой сценарий, и хуки в них стреляют независимо. Без блокировки получаем: read-modify-write `state.json` из двух процессов → потерянный водяной знак; параллельный аппенд в `dispatches.jsonl` → порванные строки, потому что строка с четырьмя полями токенов и `ext` легко перевалит `PIPE_BUF` (4 КБ на macOS).

Порванные строки опаснее, чем кажутся: они попадут в `unparsed_lines` и будут выглядеть как дрейф формата (§13), то есть **ложно разбудят уровень 2** — ровно то, чего §7.1 избегает.

Поэтому: `flock` на `.agentlog/.lock` вокруг всего прохода копирования, `state.json` пишется через temp + `rename`. Не смог взять лок за отведённое время — `exit 0`, счётчик потерь, данные заберёт следующий проход.

### 6.1 Отказы

Сборщик вызывается из хука, поэтому **никогда не роняет сессию**: любая ошибка — `exit 0`, запись в `collect.log`, инкремент счётчика потерь.

| Отказ | Поведение |
|---|---|
| Транскрипт ещё дописывается | агент в `background_tasks` со `status: running` → пропускаем, заберёт следующий проход |
| Главный лог заменён или переписан | размер и хеш первых 4 КБ не совпали с сохранёнными → перечитать с нуля. Компактификация этого **не** вызывает: проверено, она дописывает `compact_boundary` и сводку, записи до неё остаются на месте (границы на позициях 1285 и 2861 из 4017 строк) |
| Не удалось взять `flock` | `exit 0`, счётчик потерь, заберёт следующий проход |
| Сессия убита до `Stop` | `SubagentStop` не выстрелил; частичный транскрипт и `meta.json` на диске → `SessionStart` следующей сессии забирает, `transcript_truncated: true` |
| Источник ротировался раньше захвата | водяной знак указывает в никуда → пропуск помечается явно, счётчик потерь |
| Асинхронный диспатч не закрылся | `dispatch_complete: false`, токены помечены как неполные |
| `.zprof.yaml` изменился посреди сессии | новый `config_hash` с этого диспатча |
| Диск полон / нет прав | `exit 0`, счётчик потерь, громко в отчёте |

### 6.2 Асинхронный путь

Треть диспатчей идёт асинхронно (`async_launched` 1116 против `completed` 2174). Это отдельный путь, и сборщик обязан его знать.

Запись **на запуск**:

```json
{"isAsync":true,"status":"async_launched","agentId":"afbb27722ec749e56",
 "resolvedModel":"claude-haiku-4-5-20251001",
 "prompt":"Execute the long sleep task.",
 "outputFile":"/private/tmp/.../tasks/<agentId>.output"}
```

Здесь же лежит `prompt` — вход диспатча, нужный для хеширования при A/B (§8).

Терминальная запись приходит отдельно, `task-notification`:

```
<task-id>a0df02b24fd9cd288</task-id>
<tool-use-id>toolu_016eb2pkxko2518pfQ9UHsAZ</tool-use-id>
<status>completed</status>
<note>A task-notification fires each time this agent stops with no live background
children of its own. …the same task-id may notify more than once.</note>
```

Отсюда `seq` в ядре схемы: один `task-id` может уведомить несколько раз.

**Правило сшивки.** На момент запуска `toolu_…` для асинхронного диспатча ещё неизвестен, а `dispatch_id` строится на нём. Порядок такой:

1. `tool_use` в главном логе даёт `toolu_…` — это `dispatch_id`.
2. `toolUseResult` того же `toolu_…` даёт `agentId` и `prompt`. Сборщик записывает пару `agentId → dispatch_id` в `state.json`.
3. `meta.json` транскрипта содержит **оба**: `toolUseId` и имя файла с `agentId`. Это независимая проверка пары — если она разошлась с шагом 2, пишем в `collect.log` и берём `meta.json` как источник истины.
4. `task-notification` приходит с `<task-id>` (= `agentId`) и `<tool-use-id>` — закрывает диспатч, инкрементирует `seq`.

Пара `agentId ↔ toolUseId` есть в двух независимых местах, поэтому потеря одного из них не разрывает связь.

## 7. Каденция: четыре уровня

Каждый уровень запускается **только по сигналу предыдущего**. Поэтому цикл может быть регулярным и не разорять.

| Уровень | Что | Цена | Триггер |
|---|---|---|---|
| **0. Запись** | сборщик пишет в `.agentlog/` | 0 токенов | каждый диспатч |
| **1. Арифметика** | детерминированные метрики | 0 токенов | см. ниже |
| **2. Самоанализ** | `evaluator` читает свод, контракт роли и сохранённые транскрипты | десятки тыс. токенов | сигнал уровня 1 |
| **3. Shakedown** | контролируемый эксперимент | десятки тыс. (общий) — миллионы (стековый) | предложена правка |

### 7.1 Два класса метрик уровня 1

**Класс A — соответствие контракту. Норма не нужна, порог записан в самом контракте.**

- `verdict:` первой строкой, без преамбулы → 100%
- обещанный `artifact:` существует на диске → 100%
- `next:` ведёт в живую роль → 100%
- возврат разобрался по объявленной схеме → 100%
- раннер не спавнил раннера → 0

Сравнивать не с чем и не надо: «правильно» задано текстом контракта. **Работает с первого диспатча в новом проекте.** Одна поломка — уже сигнал, это не статистика.

Класс A не зависит от сложности задачи. Поэтому §8 «телеметрия меряет разные задачи, контроля нет» к нему **не относится** — это и есть основание сравнивать «до правки контракта» и «после» без изолированных хостов.

**Класс B — распределения. Нужна норма.**

- ApT (artifacts per token), стоимость задачи, `duration_ms`
- число кругов `tester`, доля `blocked`

До накопления разброса класс B **печатается в отчёте, но уровень 2 не будит**: `zprof stats` показывает «метрика вышла за грубый порог, разброс не набран (12/30 окон)». Решение — за человеком. Автоматика, жгущая десятки тысяч токенов на шум, хуже пропущенного сигнала.

### 7.2 Два разных N

| | Что | Порядок |
|---|---|---|
| `N_детект` | сигнал уровня 1 по роли | ≥ 5 диспатчей |
| `N_сравнение` | приёмка A/B (§8) | десятки на плечо |

Разница принципиальная: на 5 диспатчах плечо A даёт 5/5, плечо B — 4/5, и это ничего не значит. Для **детекта** поломки контракта хватает одного случая; для **сравнения** двух плеч на бинарной метрике нужны десятки.

### 7.3 Что выдаёт уровень 2

Не оценку, а **диф к контракту роли**. Это главное отличие от июльской спеки: баллы никого не улучшают, улучшает предложенная правка текста. Диф пишется по поведению, поэтому уровень 2 читает сохранённые транскрипты, а не только возвраты.

## 8. Тиры моделей: A/B в проде

Тир прибит в overlay, значит в телеметрии у роли всегда одна модель и сравнивать не с чем. Вариацию надо **создавать**.

**Механика.** Роль исполняется с `model`, переданным в самом вызове `Task`. Проверено (§17): сабагент с `model: haiku` в frontmatter, продиспатченный с `model: "sonnet"`, отработал на `claude-sonnet-5`. Отдельных файлов ролей под каждое плечо не нужно.

**Плечо выбирает детерминированный код, не раннер.** Раннер — стохастический агент; воспроизводимо посчитать хеш и отобразить его в плечо он не обязан, а вся конструкция §8 построена именно на воспроизводимости: без неё плечи поедут, и `N_сравнение` (§7.2) наберётся из смеси.

Поэтому:

- ту же функцию, что выбирает плечо, реализует `zprof-collect.py` в режиме `pick-arm`: на вход роль и текст задачи, на выход имя модели;
- раннер вызывает её и подставляет полученную строку в `Task`, не решая ничего сам;
- выбор — `hash(project_id + role + task_text) mod 2`, то есть та же задача при возобновлении попадает на то же плечо;
- если вызов не удался, раннер использует тир из overlay — плечо не назначено, запись помечается `ab_arm: null` и в сравнение не идёт.

Это вскрывает работу в `task-runner`, которой в §15 не было: контракт роли должен предписывать вызов, а `zprof-collect.py` — принимать второй режим. Обе части — этап 3.

**Выключатель A/B в `.zprof.yaml`** отключает вызов целиком: `pick-arm` возвращает тир из overlay.

**Приёмка.** Прод-A/B **не решает**, он отбирает кандидата. Правило приёмки из `METHODOLOGY.md` §2.6 требует семи условий; телеметрия закрывает четыре:

| Условие §2.6 | В телеметрии |
|---|---|
| преамбулы нет | да |
| возврат по схеме | да |
| `artifact` существует | да |
| тулчейн зелёный | да, через `ext` стека |
| вердикт ревьюера ≥ baseline | **нет** — суждение |
| находки C/I/M/S не хуже | **нет** — суждение |
| чистота слоёв | только через `ext` |

Поэтому цепочка такая: **A/B отбирает кандидата → стековый shakedown проверяет → человек применяет.** Выигрыш в том, что shakedown гоняется по одному готовому кандидату, а не матрицей из семи прогонов вслепую.

## 9. Shakedown

Телеметрия отвечает «что-то изменилось» — детект, дёшево, непрерывно. Shakedown отвечает «изменилось из-за этого, стало лучше или хуже» — атрибуция и приёмка, дорого, по требованию.

### 9.1 Общий shakedown (новый)

Дешёвый smoke-тест контрактов. Большинство правок от стека не зависят: формулировка, схема возврата, границы полномочий, маршрутизация раннера, работа гейтов.

- крошечный фиксированный проект — fixture в репозитории zprof, **без внешнего тулчейна**;
- полный проход цепочки `task-runner → planner → architect → implementer → tester → reviewer`;
- проверяется **форма, а не содержание** — те же проверки, что класс A уровня 1;
- гоняется на `haiku` — форму проверяет форма, не интеллект;
- цена — десятки тысяч токенов.

Смысл: ловит регрессию контракта **до раскатки на проекты**.

### 9.2 Стековый shakedown (существующий)

Как в `METHODOLOGY.md`: фиксированная фича MoodJournal, изолированные хосты, реальный тулчейн, дифференциальные прогоны через rsync замороженных фаз, асимметричное правило приёмки. 2,5–3 млн токенов на матрицу из семи прогонов.

### 9.3 Что когда гоняется

| Событие | Общий | Стековый |
|---|---|---|
| Правка контракта в `profiles/base/` | да | нет |
| Правка overlay-контракта | да | да |
| Кандидат от прод-A/B по тиру | нет | да |
| Сигнал уровня 1 | да, первым делом | если общий чистый |

## 10. Права на правку

По масштабу последствий — тот же принцип, что в `agent-write-boundaries`.

| Объект правки | Кто применяет | Обоснование |
|---|---|---|
| Пороги уровня 1 в конфиге проекта | агент, с записью в журнал | локально и обратимо |
| `model_overrides` в `.zprof.yaml` одного проекта | **только человек**, после стекового shakedown | два условия приёмки из §2.6 в телеметрии не проверяются |
| Контракт роли в `profiles/` | **только человек** | раскатывается на все проекты |
| Парсер в сборщике | **только человек** | код, раскатывается на все машины |

Изменение против v1: `model_overrides` больше не правится агентом самостоятельно. Причина — появление A/B: раньше это была правка «по ощущению», теперь она выглядит обоснованной данными, которых на самом деле не хватает.

## 12. Отчёты `zprof stats`

Первая строка каждого — счётчик потерь (С4): сколько записей не собрано, сколько транскриптов обрезано, сколько строк не распознано.

1. **Здоровье роли** — класс A по ролям, в разрезе роль × overlay × `config_hash`.
2. **Экономика и тиры** — стоимость задачи с разбивкой по кешу, **ApT** (artifacts per token — сколько принятых артефактов приходится на потраченный токен; мера отдачи роли, а не её объёма), где жгутся токены, состояние текущих A/B.
3. **Маршруты и застревания** — где цепочка уходит в `blocked`, сколько кругов делает `tester`, какие переходы мертвы. Источник — `runs.jsonl` и дерево из `parent_dispatch_id`.
4. **Дрейф профиля** — сравнение окон по `config_hash`. Низкий приоритет.

Рендер — существующий `render_html.go`.

## 13. Дрейф формата

Формат логов Claude Code меняется — это уже происходило: старый путь через `task-notification` и новый через типизированный `toolUseResult` сосуществуют. Разбор обязан замечать, что перестал понимать вход.

**Механика — графа в счётчике потерь, а не отдельная подсистема:**

1. Сборщик считает `unparsed_lines`, `unknown_toolUseResult_keys`, `dispatches_without_return`.
2. В каждой записи хранится `harness_version` (поле `version` в JSONL) и `protocol_version`.
3. Норма считается **в разрезе версии**.
4. Сигнал «дрейф формата» = `unparsed_ratio` вырос **и** версия сменилась. Это отличает «Claude Code обновился» от «наши агенты сломались» — иначе одно замаскирует другое.
5. Сигнал будит уровень 2: `evaluator` получает N нераспознанных строк-семплов и текущую схему, возвращает диф к парсеру. Применяет человек (§10).
6. Сохранённое сырьё в `.agentlog/raw/` делает фикс применимым задним числом: переразобрал — дыра в истории закрылась.

## 14. Границы ответственности за разбор

**Одна реализация разбора.** Сегодня разбор существует в Go (`cli/internal/eval/parser.go`, 446 строк). Он **удаляется**.

| Кто | Что читает | Что пишет |
|---|---|---|
| **Сборщик (python3, в проекте)** | сырые логи Claude Code, транскрипты, `meta.json`, `runs/*.md`, git | `.agentlog/*.jsonl` |
| **zprof (Go)** | **только** `.agentlog/*.jsonl` | отчёты |

Go-код перестаёт быть парсером сырых логов и становится читателем нормализованных записей. Извлечение целиком переезжает в сборщик — иначе zprof снова становится обязательным на каждой машине, а это нарушает П2.

`zprof eval` перестраивается поверх `.agentlog/` (`zprof stats --session <id>`) **на этапе 2**, а не «отдельной задачей потом». Держать второй парсер нельзя: он разъедется с первым, а сломается тихо тот, у которого нет тестов.

Знание, которое переносится из `parser.go`: сопоставление диспатчей с уведомлениями по `tool-use-id`, разбор `return_format`, проверки соответствия контракту, разрешение `Working directory:` для путей артефактов. Тесты `parser_test.go` переезжают вместе с фикстурами.

Чего в Go-парсере нет и что сборщик должен уметь сразу:

- чтение транскриптов сабагентов и `meta.json` — их он не видел вообще;
- `usage` с разбивкой по кешу — без неё стоимость не считается;
- асинхронный путь (`async_launched` → `task-notification`), треть диспатчей;
- инкрементальность через смещение;
- счётчик нераспознанного (§13).

## 16. Второй харнесс

Над проектами работает не только Claude Code. Kimi Code (`~/.kimi-code/`) устроен концептуально так же:

| Концепт | Claude Code | Kimi Code |
|---|---|---|
| Главная сессия | `<sess>.jsonl` | `agents/main/wire.jsonl` |
| Транскрипт сабагента | `<sess>/subagents/agent-<id>.jsonl` | `<sess>/agents/agent-N/wire.jsonl` |
| Крупные tool-выводы | `<sess>/tool-results/*.txt` | `agents/agent-N/tool-results/` |
| Роль | `meta.json` → `agentType` | `config.update` → `profileName` |
| Модель | `message.model` | `config.update.modelAlias`, `usage.record.model` |
| Расход | `{input, output, cache_read, cache_creation}` | `{inputOther, output, inputCacheRead, inputCacheCreation}` |

Разбивка по кешу совпадает по всем четырём измерениям.

**В этот объём kimi не входит.** Но в ядро схемы сразу закладываются `harness`, `protocol_version` и составной `dispatch_id` — иначе накопленное придётся мигрировать.

Два известных препятствия на будущее:

- идентификатор сабагента у kimi — `agent-N`, порядковый номер внутри сессии;
- zprof-роли (`implementer`, `reviewer`, `architect`…) у kimi живут **в промпте**, а не в поле `profileName` (`coder` 172, `explore` 34, `agent` 7). Определение роли для адаптера будет сложнее, чем чтение формата.

## 18. Секреты в захваченных данных

Транскрипты сабагентов и `tool-results` содержат всё, что видел агент: переменные окружения, токены, ключи, полные исходники, содержимое конфигов. По §5.3 это хранится **бессрочно и незашифрованно**, по §4.3 — в каталоге проекта, по П4 — ездит между машинами. Автоматическая чистка при этом запрещена.

Это самая опасная часть системы, и она обязана быть названа явно.

**Принятый риск.** `.agentlog/` содержит секреты в том же объёме, в каком их видел агент. Каталог не предназначен для передачи третьим лицам и не защищён шифрованием. Права — `0700` на каталог, `0600` на файлы.

**Что делается на этапе 1:**

- редакция на записи по списку паттернов: `AWS_`, `GITHUB_TOKEN`, `sk-`, `ghp_`, `Bearer `, `-----BEGIN * PRIVATE KEY-----`, `password=`, `api_key=`, содержимое `.env`. Совпадение заменяется на `⟦redacted:<имя-паттерна>⟧`, счётчик редакций печатается в отчёте (П5: молча вырезать нельзя);
- список паттернов расширяется через `.zprof.yaml`, потому что имена секретов у каждого проекта свои;
- `doctor` проверяет, что `.agentlog/` не попал в индекс git — это **не** то же самое, что присутствие в `.gitignore`: файл, добавленный до правки `.gitignore`, останется отслеживаемым;
- `doctor` предупреждает, если в `.agentlog/` найдено совпадение с паттерном после редакции.

**Чего система не делает и не обещает:** шифрования на диске, полноты редакции, защиты от чтения другим процессом того же пользователя. Редакция по паттернам ловит известные форматы, а не секреты вообще.

## 19. Декомпозиция

Объём больше одного плана реализации. Три этапа, каждый самостоятельно полезен.

**Этап 1 — сбор.** Сборщик, схема, раскатка через `apply`, три хука, `.gitignore`, проверки в `doctor`. Результат: данные копятся в каждом проекте, ничего не теряется. Ценность есть даже без единого отчёта, потому что без накопленных данных остальное невозможно. **Начинать надо с него и не откладывать** — длинные ряды (§5.3) накапливаются только вперёд.

**Этап 2 — чтение.** `zprof stats`, четыре отчёта, счётчик потерь, перестройка `zprof eval` поверх `.agentlog/` и удаление `parser.go`. Результат: класс A уровня 1 работает полностью, класс B считается и печатается.

**Этап 3 — цикл.** Общий shakedown с fixture, A/B по тирам в раннере, дифы к контрактам от `evaluator`, границы прав из §10. Результат: уровни 2–3 работают.

Пороги класса B задаются между этапами 2 и 3, когда накопится первая норма. Класс A порогов не требует и работает с этапа 2.

## 20. Открытые вопросы

- Требует ли интерактивный режим Claude Code подтверждения новых хуков после `zprof apply`. В headless (`claude -p --dangerously-skip-permissions`) хуки отработали. На дизайн не влияет, влияет на инструкцию по установке.
- **Доступность python3.** На macOS `/usr/bin/python3` — шим, работающий только при установленном Xcode CLT; без него вызов открывает GUI-диалог установки, что в headless и на сервере означает зависший хук. На Linux python3 штатно есть. `apply` должен проверять `python3 -c 'pass'` и отказываться ставить хуки, если проверка не прошла, вместо тихой установки нерабочего сбора.
- Состав fixture общего shakedown: минимальный проект, который проходит всю цепочку без тулчейна.
- Конкретные значения порогов класса B. Определяются после накопления первой нормы.
