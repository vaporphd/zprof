Очередь действий

Сигналы отсортированы по риску ошибочного решения, а не по размеру графика.

  1. P0 Контракт возврата системно нарушается

    pr-shepherd и несколько auditor-ролей имеют 0% ответов без преамбулы; у reviewer — 20%. Разбор по схеме при этом 100%, поэтому проблема именно в форме ответа.

    Следующее действиеОткрыть 10 последних нарушений, сгруппировать по config_hash, проверить контракт и scaffold возврата.

  2. P1 17.4% работы не атрибутировано

    306 диспатчей одновременно попали в unknown role и unknown model. Любое сравнение ролей и моделей до закрытия пробела смещено.

    Следующее действиеРазложить пропуски по harness version, session и причине: transcript missing, truncated, parse drift или async incomplete.

  3. P1 Implementer концентрирует 45.5% токенов

    5.96B из 13.1B токенов приходятся на 245 диспатчей implementer; среднее — 24.3M. Без outcome нельзя отличить оправданную сложность от повторной работы.

    Следующее действиеДобавить стоимость на принятый run, число повторов и разбивку до/после config_hash.

  4. P2 Длинный хвост implementer: 3.6×

    p50 = 16m 56s, p95 = 60m 53s. Агрегат скрывает небольшую группу диспатчей, определяющих время ожидания пользователя.

    Следующее действиеПоказать top-10 runs по critical-path duration вместе с причиной повторного диспатча.

Все показанные ответы разобраны по схеме, но 70–100% начинаются с преамбулы. Это локализует проблему в поведении ролей или формулировке return contract.

В production-отчёте здесь должны быть ссылки на конкретные dispatch_id, версия config_hash и сравнение с предыдущим окном.

Фактические значения.
Числа перенесены или вычислены из hft-moex-telemetry-example.html: объём, coverage, роли, модели, Class A и latency.

Не выдумано.
Там, где исходник не содержит routes, outcomes или config windows, отчёт показывает отсутствие данных вместо синтетического графика.

Следующий уровень.
