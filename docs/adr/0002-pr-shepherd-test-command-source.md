# ADR 0002: Откуда pr-shepherd берёт тест-команды в `local-green`. `## Executing` — не источник

**Date:** 2026-09-27
**Status:** accepted
**Issue:** #16 (milestone panel-2026-09-27)
**Branch:** feat/issue-16-pr-shepherd-local-green-tests

## Context

AC2/AC4 из #16 требуют, чтобы в `MERGE_GATE=local-green` pr-shepherd «извлекал
тест-команды из секции `## Executing` (строки `Test:` / fenced-команды)». Commit
`8000533` сделал это буквально (`profiles/base/agents/pr-shepherd.md` §3 шаг 2).

Требование основано на неверной предпосылке. Проверка по коду и трём проектам флота:

1. **`## Executing` генерирует zprof.** `buildExecutingTable`
   (`cli/internal/apply/tables.go:104-157`) при `zprof apply`/`sync` пишет в managed-блок
   `executing` таблицу `| Agent | Scope |`, то есть кто из агентов какими файлами владеет.
   Команд сборки и тестов в ней нет, и ни `manifest.yaml`, ни `claude-block.md` в
   overlay'ях не содержат `Test:` или `TEST_CMD:`.
2. **Живые проекты хранят команды в других местах:**
   - `hft_moex` (`backend-kotlin-jvm`, здесь уже постоянно включён `MERGE_GATE: local-green`):
     в fenced-блоке `## Project Configuration` есть строка `TEST_CMD:          cd platform && ./gradlew test`.
     Та же команда повторяется в неразмеченном fenced-блоке `## Common commands`, и в
     том же блоке лежат `ktlintFormat` (меняет файлы) и `integrationTest` (ходит в сеть,
     в sandbox брокера).
   - `jarvis-in-hermes` (`systems-rust`): в секции `### Стек и команды` строка
     `` Test: `cargo test` ``, и там же явно сказано, что `test_cmd` из managed
     `stack-config` (`cargo nextest ...`) надо игнорировать, потому что nextest не установлен.
   - `apple-health-sync` (`ios-swift`): в секции `### Стек (переопределяет managed stack-config выше)`
     команды записаны прозой (`make test`), метки `Test:` нет. Managed `test_cmd` содержит
     плейсхолдер `<SchemeName>`.
3. **Только в самом zprof `## Executing` содержит `Test:`.** Этот блок написан вручную
   внутри маркеров `<!-- zprof:begin executing -->`. У zprof нет `.zprof.yaml`
   (`todo.md:13`), поэтому генератор его ещё не перезаписывал. Это исключение, а не
   конвенция.
4. Кроме того, у каждого стекового overlay есть managed-блок `stack-config` с
   `test_cmd:` (`profiles/overlays/*/claude-block.md`). Но это шаблонный дефолт: бывают
   плейсхолдеры (`<SchemeName>`, `<see stack overlay's claude-block>`), и проекты
   явно его переопределяют (см. п.2).

Если реализовать AC буквально, `no-test-command` будет в каждом проекте флота после
ближайшего `sync`, начиная с `hft_moex` при первом же merge. Правка должна уложиться в
#16, то есть только в `pr-shepherd.md` и его зеркало, без Go и без манифестов.

## Decision

**1. `## Executing` — зарезервированный managed-заголовок.** Это таблица владения
файлами, её генерирует `buildExecutingTable`. Ни один агент не читает её как источник
команд, и никто не просит пользователя вписывать туда команды: при следующем
`apply`/`sync` содержимое будет перезаписано.

**2. pr-shepherd ищет тест-команды по всему `CLAUDE.md` в head-ветке, по уровням
приоритета.** Берётся первый уровень, на котором нашлась хотя бы одна команда.
Нижние уровни после этого не смотрятся.

| Уровень | Источник | Правило извлечения |
|---|---|---|
| T1 | Явные метки в любом месте файла, независимо от секции и маркеров | (a) `Test:`, сразу за ним команда в бэктиках. Берётся содержимое этих бэктиков, строк может быть несколько, например `` Build: `…`. Test: `…` `` → только то, что после `Test:`. (b) Строка, начинающаяся (после пробелов) с `TEST_CMD:`: значение до конца строки без хвостового `# комментария`. `<TEST_CMD>` в прозе меткой не считается. |
| T2 | Только если T1 пуст: `test_cmd:` внутри managed-блока `<!-- zprof:begin … block=stack-config -->` | Значение в кавычках. Если в значении есть плейсхолдер `<…>`, оно пропускается. |
| — | Неразмеченные fenced-блоки | **Не используются.** В таком блоке рядом с тестами лежат мутирующие и сетевые команды (пример из `hft_moex`: `ktlintFormat`, `integrationTest`), а по одному тексту нельзя надёжно понять, какая строка тестовая. |

Значения `—`, `-`, пустая строка и любые `<…>` на всех уровнях считаются
«команды нет». Найденные команды дедуплицируются по точной строке после trim.
Все оставшиеся запускаются по одной из корня репо, как и сейчас в шагах 3–5.

Почему T1 стоит выше T2: проектный текст выражает намерение владельца проекта и
переопределяет шаблонный дефолт overlay'а. Именно так пишут `jarvis-in-hermes` и
`apple-health-sync`.

**3. Если команды нет, merge не делается, как и было.** Ответ
`verdict: preflight-failed`, reason `no-test-command`,
`next: docs-writer (добавить строку `` Test: `<cmd>` `` в проектную секцию CLAUDE.md
ниже managed-блоков; не в ## Executing)`.

**4. Результат для флота:**
- zprof: T1 находит `Test:` (go, pytest). Правило не зависит от секции, поэтому
  продолжит работать, когда строки переедут из managed-блока в проектную секцию.
- `hft_moex`: T1(b) → `cd platform && ./gradlew test`.
- `jarvis-in-hermes`: T1(a) → `cargo test` (дефолт `nextest` из T2 не используется, как и
  хочет проект).
- `apple-health-sync`: T1 пуст, T2 содержит плейсхолдер. Итог `no-test-command`
  (fail-closed), чинится одной строкой `` Test: `make test` ``.

**5. Граница #16.** Меняются только `profiles/base/agents/pr-shepherd.md` (§3 шаг 2,
пункты 1, 2, 6; упоминание `## Executing` в секции reviewer-attestation, сейчас строка ~177)
и зеркало `.claude/agents/pr-shepherd.md`. Go, манифесты, коллектор и overlay'и не
трогаются.

## Consequences

- Проще: `local-green` работает на реальных раскладках флота без переезда конфигурации
  и без нового `apply`-цикла в проектах. Правило целиком лежит в промпте.
- Проще: у пользователя одна понятная точка входа — строка `` Test: `cmd` `` в своей секции.
- Сложнее: извлечение остаётся эвристикой в прозе. Нестандартные метки
  (`Tests:`, `test:` в нижнем регистре, прозаическое «прогоните make test») не
  распознаются. Это сделано намеренно: ошибка ведёт к `no-test-command`, то есть к
  отказу мержить, а не к merge вслепую.
- AC2/AC4 из #16 надо закрыть с пометкой «реализовано по ADR 0002». Буквальная
  формулировка («из `## Executing`») отменена.
- Когда zprof начнёт сам применять свой профиль (`todo.md:13`), блок `executing`
  перезапишется таблицей, и ручные строки `### Стек` пропадут. Их нужно заранее
  перенести в проектную секцию ниже managed-блоков. T1 найдёт их и там.

## Alternatives considered

- **Буквально по AC, только `## Executing`.** Отвергнуто: секцию генерирует zprof, команд
  в ней нет нигде, кроме самого zprof.
- **Весь `CLAUDE.md`, но с неразмеченными fenced-блоками.** Отвергнуто: запуск чужого
  shell-блока целиком выполнит `ktlintFormat` (мутация) и `integrationTest` (сеть) в
  `hft_moex`. Ограничиться fenced-строками, «похожими на тесты», значит добавить
  хрупкую эвристику.
- **Только managed `stack-config.test_cmd`.** Отвергнуто как основной источник: там
  плейсхолдеры, и проекты его явно переопределяют. Оставлен уровнем T2.
- **Структурное поле `test_commands:` в `manifest.yaml` и новый managed-блок
  (по образцу `executing:` / `buildExecutingTable`).** Правильное направление, но не
  для #16. Нужны правки `cli/internal/apply/` и схемы манифеста для каждого стекового
  overlay, а до нового `apply` в каждом проекте поле ничего не даёт. К тому же
  overlay знает только шаблонный дефолт, а не реальную команду проекта, так что
  проектное переопределение (T1) всё равно понадобится. **Follow-up отдельным issue:**
  «структурированный источник тест-команд: `test_cmd` из `.zprof.yaml`
  (проектный override) > `stack-config.test_cmd`; pr-shepherd читает его вместо
  прозы». #16 этим не блокируется.
